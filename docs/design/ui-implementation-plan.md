# HDIP UI 分阶段实施与验收规范

版本：1.0 · 日期：2026-10-24  
基线：`peterkis/hdip@8c400c49757e2443ceeaa7e1358ba290c786e7c6`  
适用范围：本套统一视觉规约的落地、逐场景迁移与验收。本文规定后续实施方法；不表示界面已经修改或这些检查已经执行。

## 1. 执行原则与边界

以“总规约 → 场景规范 → 组件实现 → 实际页面”形成一条一致的规则链。字体、颜色、间距、宽度、行高和交互尺寸以总规约为准，本文件只规定迁移顺序和检验方法，不复制一套数值表。

一次只完成一个可评估的闭环：先打磨变更申请列表，再迁移对象列表，最后统一详情与复杂核对。所有阶段使用现有 React、Tailwind、Base UI、TanStack Query 与路由体系，不迁移 Gr8r 的原生 DOM 渲染和 localStorage 数据层，不增建通用页面配置平台。

现有业务边界继续适用：

- 写入沿用变更申请；配置字典保留既有的授权直接维护方式。UI 不能把两者混为同一种保存语义。
- 申请仍按提交、确认、退回、撤销等既有规则推进；阅读核对状态不是业务审批状态。
- 正式对象的身份、代码、期间、关系以及历史保护规则，不由视觉重构修改。
- 人员与任职保持当前共享目录范围，不借此次设计增加 HR 岗位、资质、临床授权、排班或账号权限模块。
- 业务有效期是闭区间；审计时间沿用项目不带时区的时间戳显示约定，不在 UI 中擅自转换时区。
- `web/src/api/generated/` 由 orval 生成，不手工编辑。需要接口变化时，按后端契约、OpenAPI、生成客户端的原有流程推进。

依据：[CLAUDE.md](https://github.com/peterkis/hdip/blob/8c400c49757e2443ceeaa7e1358ba290c786e7c6/CLAUDE.md)。

## 2. 文档与代码的唯一权威

### 2.1 建议落库方式

| 内容 | 建议位置 | 权威职责 |

本交付中的拆分文件用于审阅和导入。实施时将总规约合并到现有 `ui-tokens.md`，并把本文件与场景文档按上表落位；不要让“旧规范”“新规范”“v2规范”同时长期宣称权威。

### 2.2 同步动作

1. `ui-tokens.md` 明确适用版本、已落地阶段和当前规范入口。
2. 将旧文档中相互矛盾的表格边线、页面宽度、导航范围等说明一并收敛。状态色按总规约 R-COL：保留既定“停用红、结束灰、计划浅黄”；停用以低强度状态标签表达，不自动变成错误警报。附件中的“停用改灰”属于未采纳的参考建议，不由各页面各自实施。
3. 修订 `CLAUDE.md` 的视觉规范摘要与索引，使其链接到唯一主入口，不抄写全部数值。
4. 更新 `/design` 的说明、样例与日期，特别是任务列表、字段比较表、中文长名称、弱化元信息与状态标签的组合。
5. 只有接口、导出或业务规则确实改变时，才同步相应契约和领域文档；纯视觉阶段不要求数据库文档生成。

## 3. 阶段地图

| 阶段 | 交付闭环 | 主要变更 | 明确不包括 |
| --- | --- | --- | --- |
| U0 规范接入 | 文档与实现边界一致，可以开始试点 | 统一规范入口；记录现状与目标；新增需要的语义角色 | 全站替换所有令牌或重写布局 |
| U1 申请列表试点 | 从列表识别一件事、进入详情、返回原位置 | 摘要层级、标题链接、状态单选导航、元信息、列表宽度 | 新业务摘要接口、“待我处理”、确认捷径 |
| U2 公共件与对象列表 | 已验证模式扩展到真实台账 | 页头、工具栏、连续行、比较表、列表状态、对象列表 | 任意视图编辑器、多套重复表格框架 |
| U3 详情与复杂核对 | 对象阅读、问题定位、正式核对连续可用 | 属性区、区块、差异、图与清单、时间线、表单 | 改变拆并、期间、审批与权限规则 |
| U4 按需能力 | 明确场景驱动的一项增强 | 可选摘要契约、侧边预览、固定视角、快速定位 | 一次性同时建设全部增强能力 |

U0–U4 是 UI 实施阶段，与现有 A1、S0、I1、R1 等业务计划无关。它们不改变人员模块的推进顺序。

## 4. U0 规范接入

### 4.1 工作内容

- 记录工作分支实际 HEAD；若与本文件基线不同，先检查涉及页面、组件和契约的增量，保留后续已完成的修复。
- 对照当前 `tokens.css`、`index.css`、`layout.tsx` 与 `database.tsx`，登记要保留、重定义、补充、退出使用的规则。
- 保留三层令牌结构；为总规约新增的页面类型、文字角色或密度补充语义令牌。
- 若新增字号类，检查 `lib/utils.ts` 中 tailwind-merge 的字号分组，保证它不会与 `text-fg-*` 颜色类互相误删。
- 使用页面类型或轻量组件参数支持新布局，先保持未迁移页面的现有表现。避免负 margin、任意 calc 和逐页复制布局绕过外壳约束。
- 令牌声明必须在真实组件上生效：检查 Button、输入框、表格、页头实际 computed style；不能只更改“控件高度”令牌却保留组件内不一致的固定高度。主按钮的默认、hover、pressed 也分别测量文字对比，检查浅色、深色和已支持强调色组合。

当前已核实的实现事实：

| 项目 | 基线情况 | 实施注意 |
| --- | --- | --- |
| `text-xs` | 被重映射为界面正文角色，正常根字号下为 14px | 不能按 Tailwind 默认 12px 批量修正 |
| 侧栏与顶栏 | 240px 与 44px 令牌 | 根据总规约保留或集中调整，不逐页覆写 |
| 桌面正文 padding | `Layout` 实际使用左右各 64px | 96px 旧令牌并非此处的实际值 |
| 申请列表 | 内层另外限制到 900px | 迁移时同时检查外层和内层约束 |
| 表格 | 基础件存在横线与细竖线 | 按连续工作列表与字段比较表明确用途 |
| `/design` | 有独立的外壳和组件示例 | 不能只改业务页面而留下旧样例 |

### 4.2 完成条件

- 能从唯一主规范找到每条尺寸、颜色和布局规则。
- 已区分“源码现状”“目标规范”“尚未实现能力”。
- 新角色具备浅色和深色主题下的明确行为。
- 未迁移页面没有因全局默认值变化产生意外缩放或截断。

### 4.3 回退与暂停条件

文档接入可单独完成。若某个新全局默认值影响大量无关页面，改为显式页面模式接入，再推进 U1。不要为解除布局限制而临时覆盖整站组件的默认密度。

### 4.4 可直接使用的实施 prompt

> 在新版 HDIP 仓库执行 UI 阶段 U0。先读 CLAUDE.md、docs/design/ui-tokens.md、本套统一视觉规约及场景规范，并记录实际 HEAD。核对 8c400c4 之后的相关增量，保留已有修复。将总规约合并为现有 ui-tokens.md 的唯一权威，明确原始 notion-design-md.md 是参考材料，修正文档中的宽度、表格边线与导航矛盾。为后续试点补充总规约要求的语义角色和轻量布局模式，暂不切换未迁移页面。保留 text-xs 的 14px 映射、Base UI 体系、现有图标封装与状态色来源。新增字号类时同步检查 lib/utils.ts 的合并配置。更新 /design 的规范索引与已实现样例。不要修改 API、数据库或业务规则。输出改动文件、规则对应关系、实际验证和未验证项。

## 5. U1 变更申请列表试点

### 5.1 当前可用数据

仅使用列表接口已经返回的：

`id`、`status`、`note`、`item_labels`、`created_by`、`created_at`、`submitted_at`、`confirmed_at`、`returned_at`、`cancelled_at`。

详情的对象片段、业务期间、动作权限不能被当成列表已有字段。最新基线的列表说明已经复用敏感信息隐藏逻辑，展示层必须继续使用服务端结果。

来源：[ChangeRequestSummary](https://github.com/peterkis/hdip/blob/8c400c49757e2443ceeaa7e1358ba290c786e7c6/web/src/api/generated/model/changeRequestSummary.ts)、[说明脱敏回归](https://github.com/peterkis/hdip/blob/8c400c49757e2443ceeaa7e1358ba290c786e7c6/api/tests/test_rules_persons_masking.py)。

### 5.2 范围

- 以安全的已有说明或类型汇总提供主要链接；无说明、已隐去内容、多个类型时有确定的回退文案。
- 编号降为辅助识别；申请人、最近处理时间直接可见。
- 状态采用明确的单选切换，保留其真实名称。不要把“已提交”改称“待我处理”。
- 采用总规约的连续工作行；不在每行周围重复增加卡片、阴影与圆角。
- 保持原生链接语义，支持键盘进入、新标签页打开和浏览器返回。扩展点击区域时，不遮挡选择、文本复制或独立操作。
- 状态筛选、后续新增的轻量搜索等可恢复条件使用明确的 URL 参数；滚动与选中记录可随路由返回恢复，不把敏感记录内容存入 URL。
- 标题过长时允许按总规约换行或截断，并提供键盘和触屏可用的完整内容查看方式，不能只依赖 title 悬停。

主要文件：`pages/changes.tsx`、`components/layout.tsx`、`components/kit/database.tsx`，以及实际需要的令牌和桥接文件。

### 5.3 完成条件

- 一份申请能从主体内容区域进入详情，编号不再是唯一入口。
- 说明缺省、说明过长、说明已隐去、变更类型很多的情况均能理解。
- 任何状态筛选结果都与 URL、选中态和返回行为一致。
- 页面没有为了补齐摘要，对每一行额外请求详情。
- 用户能从申请详情返回原筛选范围；状态或数据变化后，焦点返回仍有合理目标。
- 提交、确认、退回、撤销和核对门槛完全沿用既有接口与规则。

### 5.4 停止扩张条件

若准确标题需要对象名称，或希望新增“生效日”“去确认”等字段，先按现有字段完成 U1，把明确的数据缺口列入 U4。不得借此提前扩建整套待办系统。

### 5.5 可直接使用的实施 prompt

> 执行 HDIP UI 阶段 U1，只改进变更申请列表及它必需的公共样式。使用场景规范中的申请列表布局。先检查 ChangeRequestSummary 的实际字段，不添加臆测的对象名称、生效日期、待办归属或动作权限。主阅读内容采用服务端已有安全说明，缺省时使用类型汇总；编号与申请人进入辅助层，主摘要是明确链接。把状态筛选改为单选导航，保留真实状态名和可恢复范围。实现加载、失败、无申请、无筛选结果、长内容和隐藏内容的表现。不要逐行查询详情，不改动申请状态机，不在行上提供未经权限支持的确认按钮。只在此页面启用需要的新布局模式，保留其他页面。运行现有前端构建，走查“识别申请—进入详情—返回列表”，记录实际截图、未执行项和仍需后端支持的增强点。不得把未运行的项目写成通过。

## 6. U2 公共件与对象列表

### 6.1 迁移顺序

1. 从 U1 提取已被实际使用的页头、状态导航、连续行与元信息规则。
2. 部门列表与层级树。
3. 服务单元列表。
4. 主体、院区和分类方案。
5. 编码映射台账。
6. 人员名册、部门任职与负责人一览。

每批采用相同字段口径做前后对照，避免同时更改显示、排序、数据范围与导出规则。布局遵循 R-LAY，文字与密度遵循 R-TYP，连续行与比较表遵循 R-ROW；不得在阶段说明或组件默认值中另起尺寸标准。

### 6.2 组件分工

- 连续工作列表：用于申请、事件、待核对记录；主要读一件事的摘要。
- 字段比较表：用于台账横向对照；保留真实表头、列语义与需要的局部竖线。
- 树形列表：用于层级；展开按钮、对象链接与选择框各有独立语义。
- 工具栏：常用视角、当前筛选、搜索与次级操作层级清楚；无需为了统一外观让所有页面拥有全部控件。

尽量扩展现有 `DbTable/DbRow/DbCell/DbToolbar` 的小型明确模式。只在表达结构确实不同的时候拆分轻量组件；不创建能任意解释配置 JSON 的通用渲染器。

### 6.3 完成条件

- 名称、代码、状态、相关对象和日期有稳定的阅读位置。
- 对象类型不同但名字相近时仍能区分，院区与行政隶属不混淆。
- 已选条件可见、可清除；不通过颜色单独说明状态。
- 批量选择保持原范围与数量语义；操作仍只生成既有多项草稿。
- 人员导出继续与页面支持的筛选一致；无权字段、未知值与“未登记负责人”的语义保留。
- 新组件可在 `/design` 查看长中文、代码、状态、选择与键盘焦点的组合。

### 6.4 回退条件

某一公共件变化影响未迁移页面时，回退该默认值并使用显式模式。不要为了迁移一个台账，把全站所有标签、表格和表单一次性替换。

### 6.5 可直接使用的实施 prompt

> 执行 HDIP UI 阶段 U2，先从已经通过 U1 走查的模式提取最少公共规则，再逐批迁移对象列表。此次只处理所选的一批页面，逐项遵照场景规范中的列顺序、名称与代码层级、状态和相关对象表达。保留查询参数、日期口径、筛选、批量草稿和导出契约；不同表格用途使用明确模式，禁止一套默认改动意外影响全站。组件继续使用语义令牌、Icon 封装与现有 Base UI。每批更新 /design 中对应样例，构建后完成真实筛选、定位、进入详情、返回和相关导出走查。输出本批涉及页面及剩余迁移清单，不为未来页面提前抽象。

## 7. U3 详情、表单与复杂核对

### 7.1 调整范围

- 对象详情统一页头、属性区、区块、相关对象引用、日期和历史展示。
- 区块排序反映维护问题：当前对象是什么、与谁有关、哪些信息需要处理、历史如何变化。
- 变更详情继续按现有业务组组织，保留主语、动作、关联对象、日期的层级。
- 核对进度、问题跳转与正式动作可见且不互相遮挡。
- 表单保持按名称选择引用对象、代码分配、字段级错误、一次保存到草稿的既有动线。
- 关系图与矩阵保留当前业务含义、图例、口径说明和已有的窄屏替代方式。
- 时间线清楚区分业务生效日与处理时间，不将最近操作顺序误写为业务期间顺序。

主要文件按场景选择：`change-review.tsx`、`problem-card.tsx`、`kit/property-list.tsx`、`kit/section.tsx`、`kit/steps.tsx`、`forms/`、`version-timeline.tsx` 及相应页面。

### 7.2 不改变的既有交互决定

- 申请详情不新增已明确移除的重复概览卡片。
- 主提交或确认动作不在页头、页底反复出现；是否需要固定区域按总规约处理，保持一个明确动作位置。
- 不提供逐项删除来拆散组织变更申请。
- 来源对象名称仍是可辨认文字，动作与对象引用有不同表现。
- 查看日期变化仍进入查询键，确认申请后仍使相关数据失效重取。
- 页面阅读勾选和后端可执行权限分别判断。

### 7.3 完成条件与边界

完成一条正常流程和一条原本会失败的流程即可验证所改动的场景，例如“保存草稿并提交”与“日期冲突定位”。只针对受影响规则运行已有测试；不为圆角、行高或标签排列新增大量快照测试。

如果页面改造需要改变前后内容的业务含义，停止把它作为纯视觉修改处理，单独定义契约变更；已可独立完成的样式与布局部分正常交付。

### 7.4 可直接使用的实施 prompt

> 执行 HDIP UI 阶段 U3，本次选择一个对象详情或一类核对场景，按场景规范调整属性、区块、问题与动作位置。先读现有业务规则和已有组件，保留按期间读取、确认前预演、完整事务、逐组核对、敏感信息隐藏和权限返回机制。表单继续按名称选择引用、按原规则分配代码、字段就地校验。不要增加逐项删除、快速确认或更改业务状态的拖拽动作。检查长中文、复杂引用、历史记录、未来日期、窄屏、键盘和减少动效。只跑与实际改动风险对应的现有检查，并记录一条正常流程和一条错误恢复流程的结果。同步对应规范与 /design 示例。

## 10. 视觉与交互验收

### 10.1 视口与环境

| 环境 | 检查重点 |
| --- | --- |
| 1366 × 768 CSS 视口 | 页头、工具栏、首屏数据和关键动作是否拥挤 |
| 1440 × 900 CSS 视口 | 默认桌面布局、对齐线、连续行和详情阅读 |
| 1920 × 1080 CSS 视口 | 列表是否过度拉长，文档阅读宽度是否失控 |

上述矩阵用于选择有代表性的验证点。每次局部改动以所影响的断点与页面为主，公共布局改变时才覆盖完整矩阵。

### 10.2 共通验收条目

| 编号 | 验收项目 | 通过标准 |
| --- | --- | --- |
| Q01 | 对齐 | 页面标题、主工具栏、主要内容共享总规约定义的内容边线 |
| Q02 | 信息主次 | 名称或主要变化先被读到，编号和元信息不抢占第一层 |
| Q03 | 密度 | 行内容完整可达，长中文不会因固定高度被裁切 |
| Q04 | 表格用途 | 工作列表与字段比较表分别采用规定边线，不逐行套卡片 |

| Q06 | 链接语义 | 主要对象名称是链接；键盘、浏览器返回和新标签打开可用 |
| Q07 | 筛选范围 | 条件、结果和计数一致，条件能清除，返回后范围可恢复 |
| Q08 | 状态表达 | 状态有文字，颜色取统一映射，不仅靠色点说明含义 |
| Q09 | 日期表达 | 查看日期、业务期间、最近操作时间分别可理解 |

| Q11 | 错误恢复 | 焦点能到达问题字段或变更项；修正后仍保留必要上下文 |
| Q12 | 空与未知 | 加载、失败、无数据、无筛选结果、未登记、无权限不相互混用 |

### 10.3 可访问性指标的使用方法

- 普通正文、辅助信息和有意义的占位提示，按至少 4.5∶1 检查；大字的例外只有在符合对应字号定义时使用。引用：[WCAG 2.2 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。
- 识别控件、状态和关键图形所必需的视觉信息，按与相邻颜色至少 3∶1 检查。并非所有装饰分隔线都必须加深到 3∶1。引用：[WCAG 2.2 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。
- 点击目标依据总规约的控件尺寸实施；24 × 24 CSS px 是 WCAG 2.2 AA 的最低规则之一，另有间距、行内等例外。小图标可以保持视觉尺寸，但应提供合理的真实点击区域。引用：[WCAG 2.2 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。
- 普通文字与控件应在窄视口重排；含横向比较含义的数据表可在自身区域滚动，不据此允许整个页面横向溢出。引用：[WCAG 2.2 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)。

这些条目是本项目选择的验收要求。完成部分条目或观察一张截图，不等于已经证明完整 WCAG 合规。

## 11. 三条最低任务走查

### T1 识别并打开一份申请

起点：有多种状态、部分长说明和缺省说明的申请列表。  
任务：找到一份已提交申请，说明它涉及什么，从主要内容进入详情。  
观察：是否必须反复悬停或进入多份无关详情；能否看出申请人和最近处理；状态名称是否准确。  
完成：无需猜测隐藏字段，列表与详情的基本识别一致，键盘也能进入。

### T2 连续查看并返回

起点：按对象类型或状态缩小后的列表，已滚动到中部。  
任务：依次查看几条记录，返回后继续原范围。  
观察：筛选、滚动、选中态、焦点是否保留；记录更新或消失后是否有合理落点。  
完成：无需重新建立筛选条件，页面不把焦点丢到无关位置。未引入预览阶段时，以现有完整详情返回路径验收。

### T3 核对与错误恢复

起点：一份正常草稿与一份含既有可复现校验问题的草稿。  
任务：核对正常草稿并按既有权限提交；定位错误草稿中的问题并返回调整入口。  
观察：核对进度和业务状态是否混淆；问题定位是否准确；主要操作是否被固定区域遮挡；是否出现绕过原有规则的路径。  
完成：正常与错误路径都可理解，UI 改造没有改变服务端判断和历史规则。

不预先承诺“效率提高百分之多少”。若希望衡量改进，使用相同数据和相同任务记录进入详情次数、重设筛选次数、定位错误次数与完成用时，说明样本和测试环境。
