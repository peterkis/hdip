## 2. 核心判断

HDIP 已经拥有可继续演进的视觉基础：`--hd-` 命名空间、原始值—语义值—桥接三层结构、中文系统字体、统一图标入口、数据库列表基本件、属性列表、标签色、全局查看日期、变更申请核对结构，以及适用于关系图和桑基图的专用表达。此次统一规范应整理这些既有能力，再补齐布局比例、交互状态和页面模板。

本轮已经确定：直接重写 `docs/design/ui-tokens.md` 为唯一产品规范，原始 Notion 抽取文档保留参考地位；保留现有蓝色品牌体系，修复真实按钮状态与深色主题组合；保留项目已确定的“停用红、已结束灰、计划浅黄”，停用以低强度红色 Tag 表达，不将整行染成警报；默认列表仅横向分隔，矩阵与跨列对照显式启用竖线；保留运营关系的流动虚线语义，并提供减少动效时的静止等价表达。工作列表、文档详情与关系画布采用不同页面模板，具体尺寸统一从主规范读取。

目前的不一致主要来自两类原因：一是营销网站的原始抽取报告仍被当作上位规范；二是持续增加的场景规则没有同步清理旧条目，有些 token 已定义但控件没有消费它。仅替换几个颜色或字号，不能解决这些问题。

### 三条必须准确表述的现状

1. **`text-xs` 当前为 14px。** `index.css` 第 21 行将它映射为 `--hd-type-ui-size`；其定义指向 14px。不能套用 Tailwind 默认含义，将现有正文误判成 12px。
2. **桌面正文实际水平内边距为 64px。** `layout.tsx` 第 73 行是 `lg:px-(--hd-space-64)`。`--hd-page-padding-x` 虽定义为 96px，但该正文容器没有使用它。迁移前后比较必须写“当前实际 64px”，不能写“当前 96px”。顶栏另用 `px-3`，当前两者没有共享内容起线。
3. **普通 Button 实际为 28px 高。** `button.tsx` 的 default 是 `h-7`，不是 `--hd-control-height` 定义的 32px。`sm` 为 24px、`xs` 为 20px、`lg` 为 32px。只改 token 不会自动让这些按钮变高。[S3][S4][S5][S7]

## 4. 应继续继承的 HDIP 设计决定

| 既有决定 | 保留原因 | 统一规范中的写法 |
| --- | --- | --- |
| 名称先于内部代码 | 维护人员按业务对象工作 | 名称为主要识别信息；稳定代码作为辅助核对信息，并可复制 |
| 名称选择关联对象 | 减少错误引用 | 保留可搜索选择器及同名对象上下文，不退回代码输入 |
| 院区、部门、单元代码由系统分配 | 已实现且属于业务规则 | 代码只读；保存前显示分配提示；外部代码与其他对象代码不能一概套用此规则 |
| 全局查看日期 | 主数据有效期视图需要明确时间上下文 | 在页面可见位置保持日期及“回到今天”；与变更生效日分开命名 |
| 创建变更进入草稿申请 | 符合当前治理闭环 | “保存到申请”“提交申请”“确认申请”是不同结果；视觉便利不绕过业务步骤 |
| 属性列表与 Section | 适合实体详情 | 保留共享结构；允许复杂内容采用更宽的数据区，不恢复多层 Card 套 Card |
| Tag 与 Badge 分工 | 状态与计数不应混同 | Tag 表达带标签的语义或分类；Badge 用于数量和附注 |
| 桑基图与实体关系图分工 | 数量流与关系边含义不同 | 明确图题、口径和点击结果；图表能回到可核对的明细 |
| 问题卡：事实—日期—怎么改 | 校验结果可行动 | 保留名称化事实、定位入口和持续显示的纠正建议 |
| 变更核对的主语—谓语—宾语 | 已解决名称与动作混淆 | 名称正文色，动作语义色，关联对象细边框；不得给每个字段都加彩色底 |
| 拆并后的自动结束项、外部办理项 | 对业务后果有意义 | 与本申请直接变更项区分，保持可展开、可核对 |
| 中文系统字体与统一 Icon | 满足内网、Windows / macOS 环境 | 继续使用现有封装，统一真实尺寸和线宽，不新引入视觉框架 |

## 6. 已计算的颜色风险及限制

以下数值用固定版本 CSS 的 sRGB 色值与标准相对亮度公式计算，按指定底色合成透明度；不是屏幕截图取样，也不是整站可访问性认证。实际组件若被其他样式覆盖，仍需读取浏览器最终计算样式确认。

| 当前组合 | 计算对比度 | 对新规范的含义 |
| --- | --- | --- |
| 浅色主按钮：白字 / `#0075de` | 4.57:1 | 接近普通文本 4.5:1 门槛；其它状态不能随意变浅 |
| 浅色按钮悬停：白字 / `#0075de` 80% 透明度叠白底 | 3.34:1 | S7 的 hover 不能仅凭默认态通过而放行 |
| 深色主按钮：白字 / `#097fe8` | 4.03:1 | 当前 14px 文本需调整前景或背景 |
| 深色 purple 的链接：`#7237ae` / `#191918` | 2.41:1 | 强调色块覆盖深色语义后产生可读性风险 |
| 深色 teal 的链接：`#0a7b77` / `#191918` | 3.45:1 | 同上 |
| 黑色 30.2% 透明度 / 白底，当前 disabled 色 | 2.12:1 | 禁用控件有不同适用条件，但有用 placeholder 不应借用此角色 |
| 黑色 54.1% 透明度 / 白底，当前 muted 色 | 4.61:1 | 当前辅助正文在该组合上可满足基本门槛；换底色仍需复核 |
| 白色 45.9% 透明度 / `#191918`，深色 muted | 4.61:1 | 同上，不能推论在所有浮起表面都合格 |

W3C 对普通文本要求至少 4.5:1，并明确占位文字、悬停和焦点态文字也纳入；大字、禁用与装饰等有具体例外。参考：[WCAG 2.2 1.4.3 Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。这里报告的是明确色值组合，不应直接扩展成“整个 HDIP 不合规”的结论。

现有 20px `Button xs` 同样需要结合真实可点击区域与相邻间距判断。WCAG 2.2 的 24×24 CSS px 最小目标存在间距、行内、等效入口等例外；不能看到一个 20px 图形就自动判整个页面失败。新规范宜让重要高频操作直接达到足够的命中面积。参考：[WCAG 2.2 2.5.8 Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。

## 7. Gr8r 应提供的方法，以及与 HDIP 的边界

| 参考机制 | 可吸收的方法 | HDIP 必须保留的边界 |
| --- | --- | --- |
| 所有内容边缘共用 gutter | 页面起线稳定，减少缩进层层叠加 | 页面可有不同最大宽度，但要用同一布局模型计算起线；不能只改标题 padding |
| 暖灰侧栏 + 白工作面 + 轻边界 | 通过表面与文字权重区分层级 | 仍保证中文文字、关键字段、禁用原因与焦点可读 |
| 连续统计条 | 数字紧凑且可以成为筛选入口 | 口径真实、可解释、可下钻；加载不是0；不要为漂亮而编造指标 |
| 主任务区与辅助信息区 | 当前要处理的内容占主要面积 | 申请核对依然围绕分组、问题、后果和确认语义；不要被通用任务卡替代 |
| 行点击/详情抽屉 | 保留筛选、滚动与对象上下文 | 抽屉用于预览与轻操作；复杂拆并/多项核对有完整页面；关闭与切换不能丢未保存输入 |
| 可见 filter chips | 用户知道当前为何只看到这些数据 | 继承 HDIP URL 筛选；保存视图是查询配置，不是实体、分类或权限数据 |
| 行内操作和局部菜单 | 降低固定按钮墙的视觉噪声 | 只读实体属性与治理变更区分；不能点击颜色标签就直接生效 |
| 小幅反馈 | 操作结果在原位置可见 | 确认、校验、事务成功仍以真实结果为准，不做前端假成功 |
| 多视图 | 同一数据可按任务换一种读法 | 列表/树/图/矩阵按需要开放；不为统一风格强行补齐看板、日历、文件等所有视图 |
| Command palette | 快速找对象与入口 | 先提供可解释的对象命中；不能让搜索选择直接执行高影响业务动作 |

Gr8r 是纯前端演示型实现，其数据来自 seed/localStorage；不能直接继承它的认证、保存、权限或状态修改模型。其图形语言可作为设计参照，HDIP 继续使用自己的组件、领域模型、API 与业务门槛。

## 9. 推荐的实施次序与停止边界

1. 先发布统一文档和旧条目替换清单，消除彼此矛盾的指令；不把当前实现描述成目标已完成。
2. 修改一组共享基础：布局起线、文字角色、Button/Input/Select 真实尺寸与状态色。保持旧桥接名称兼容，避免全仓库机械替换。
3. 用“一个普通实体列表 + 一个实体详情 + 一张包含问题的变更申请”作为贯穿样本，验证视觉与业务闭环后再推广同类页面。
4. 沿现有 `kit`、`forms`、`layout` 组件演进；按使用场景补充明确的 variant。不要为视觉整理新增通用 schema 平台、复杂配置引擎或第二套应用状态架构。
5. 最后同步 `/design` 与旧文档。确认对应消费方生效后，再删除无用 token 或兼容映射。

本次有意义的验证集中在：真实计算字号与高度、统一起线、长中文名称、单行/多行列表、浅深主题与主按钮各状态、键盘焦点、局部横滚、未保存退出提示，以及“保存草稿—提交—确认—查看有效日期”不被视觉改造改变。没有证据需要重写全站测试；应针对上述具体剩余风险验证。

## 10. 交付前防矛盾复核项

- 统一规范里的基线写的是 `text-xs=14px`、桌面实际正文内边距64px、Button default28px；96px仅为当前未被该正文容器消费的 token。
- 字号、行高、控件高、页面宽度只在一个权威表出现；场景规范引用该表，不另写不同值。
- 页头/工具栏/表格对齐规则与最大宽度、侧栏宽度共同计算，不承诺只改 gutter 就能在所有屏幕同一绝对坐标。
- 所有颜色规范明确所属语义：状态、分类、图表；pending与计划的语义说明完整。
- 草稿、提交、确认与指定日期有效性没有被混成一个状态；UI 不创造不存在的后端状态。
- 编码策略按对象类型，不把院区/部门/服务单元的系统分配扩成所有代码。
- 单主动作规则考虑活动弹层，但申请页仍遵守已定的单一提交/确认入口。
- 预览抽屉与正式维护/确认页面边界清楚；行内便利不会绕过真实业务校验。
- 原有用户明确选定的核对语句层级、轻问题卡、语义色、图形表达没有被通用模板意外覆盖。
- 原始来源的评分、字体下载建议和自动分类都没有升级成已验证的产品事实。
