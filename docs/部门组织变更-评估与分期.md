# 部门组织变更（拆分、合并等）：评估与分期

> 依据：Peter 2026-10-17 对部门拆分、合并的意见（下称“意见”）。本文评估意见中的核心模型在本项目里怎么落，哪些现在做、哪些以后做。
> 状态：**第一期已实施（2026-10-17）**。Peter 同意第 6 节五项决定。实现：迁移 0012、变更项 `department.reorganize`、承接清单接口 `GET /api/departments/{id}/dependencies`、部门页“组织变更”向导与“沿革”、导出 `department-lineage`；剧本 18–20 与 `test_rules_reorg.py`。

## 1. 结论

- **采用意见中的核心模型**：部门身份 + 部门状态版本 + 组织变更事件 + 逐项依赖处置 + 实施与核验记录。
- **按意见把三件事分开建设：**
  - **沿革能表达**：第一期完成。
  - **承接受控执行**：第一期只覆盖本平台已有的对象。
  - **全院自动迁移**：不做自动迁移，以后分阶段做实施与核验回执。
- **第一期的目标是业务流程跑通。** 一张变更申请里做到：
  1. 写清身份结论：谁存续、谁退出、谁新设；
  2. 逐项处置受影响的依赖；
  3. 确认时整体生效，任何依赖没有处置都不能确认。
- **大部分构件已有，只需新增两件。**
  - 已有的：
    - 身份表与版本表；
    - 一张申请多项变更、一个事务；
    - 申请全部应用后的统一校验（`_check_units`、`_check_org`、`_check_codes`）；
    - 服务单元改挂部门；
    - 行政隶属调整；
    - 外部编码解释的开始与结束。
  - 新增的：
    - 组织变更事件表；
    - 生成“承接清单”的向导。

## 2. 意见中的模型与现有构件的对应

| 意见中的模型 | 本项目现状 | 第一期要做的 |
| --- | --- | --- |
| 部门身份 | `department`：代码永久绑定，id 不复用 | 不变 |
| 部门状态版本 | `department_version.lifecycle`：`PREPARING / ACTIVE / SUSPENDED / REVOKED / SUPERSEDED` | 码值不变，语义按意见写明（见 3.2）。`SUPERSEDED` 只能由组织变更事件产生，不能手工改 |
| 组织变更事件 | 无；服务单元有 `service_unit_lineage`，但它只是一对前身与后继 | **新增** `department_change_event`（类型、生效日、正式依据、申请）和 `department_change_participant`（部门、角色：原部门 / 结果部门、身份结论：存续 / 退出 / 新设、承接范围说明） |
| 逐项依赖处置 | 申请里的各个变更项，确认时统一校验 | **新增承接清单**：系统按生效日列出每个退出部门的全部依赖，逐项选处置方式，生成对应的变更项；有依赖没处置就不能确认 |
| 实施与核验记录 | 无（MVP 不对接下游系统，也不做发布投递） | 第二期 |

## 3. 第一期：现在做

### 3.1 事件类型：先定身份，不按名称推断

向导的第一步就是身份裁决，由操作人明确选定。系统不因为名称从“呼吸内科”变成“呼吸一科、呼吸二科”就推断出结论。

| 类型 | 身份结论 | 原部门状态 |
| --- | --- | --- |
| 整体拆分 | A 退出，新设 B、C；记录 A → B + C | 被替代 |
| 分设（原部门存续） | A 保留身份（可在同一张申请里改名），新设 B；记录 A → A + B | 仍为正式履职 |
| 吸收合并 | A 退出，并入已有的 B，B 身份不变 | A 被替代 |
| 合并新设 | A、B 退出，新设 C | A、B 被替代 |

意见中的其他几种情况，都不建组织变更事件：

| 情况 | 处理 |
| --- | --- |
| 原部门保留作为上级，下设两个子部门 | 新建部门，再设上级 |
| 只是把业务分成几个门诊或住院单元 | 部门不变，走服务单元的拆分 |
| 多个部门只是统一主任、排班或专业管理 | 走专业管理、协作关系 |
| 重复数据归并（两条记录原本就是同一个部门） | 是身份纠错，第一期不做，留在第二期。在第二期之前，不允许用“合并”来代替纠错 |

### 3.2 状态线

码值不变，只按意见把语义写清楚：

| 码值 | 中文 | 语义 |
| --- | --- | --- |
| `PREPARING` | 筹备 | 有筹备依据、尚未正式履职（对应意见中的 PLANNED） |
| `ACTIVE` | 正式履职 | |
| `SUSPENDED` | 暂停履职 | 整个部门暂停。局部停诊、装修应作用在服务单元上，用单元的“暂停” |
| `REVOKED` | 撤销 | 永久退出，没有组织承接（对应意见中的 DEPRECATED） |
| `SUPERSEDED` | 被替代 | 只由组织变更事件产生，事件里写明承接部门与范围；不自动重定向 |

### 3.3 承接清单（逐项处置）

清单只针对每个退出的部门，在生效日 T 列出。所有处置都在同一张申请里生成变更项，确认人能逐项看到。

| 依赖 | 可选处置 | 默认 | 说明 |
| --- | --- | --- | --- |
| 服务单元（所属部门 = 运营主责） | 改挂到某个结果部门（单元身份不变）、单元退出、单元另行拆分 | **无默认，必须选** | 已有规则保证：退出部门不能再有在用单元 |
| 下级部门 | 改挂到某个部门、改为一级部门、自身退出 | **无默认**，不默认挂到第一个新部门 | 已有规则保证：退出部门不能还有下级 |
| 指向该部门的外部编码解释 | 结束解释（历史仍指向原部门）；如外部系统确有重新分配记录，另新增解释到新部门（须写依据） | 结束解释 | **不允许直接改指向**；没有新解释的代码在 T 之后进入“待裁决”，交台账处理 |
| 指向服务单元的外部编码 | 不变 | 不变 | 单元身份没变 |
| 部门上的分类 | 原部门的赋值到 T-1 结束；结果部门的分类逐个确认，原值只作为候选预填 | 结束（原部门） | 不自动继承 |
| 专业管理、协作、院区管理关系 | 原部门的关系自动结束（已有行为）；需要的关系在清单里为结果部门重建 | 结束 | |
| 别名、检索码 | 随原部门结束 | 结束 | |

存续的部门（分设里的 A、吸收合并里的 B）不强制处置，默认保持不变，因为它确实没有变。但清单会把它们的依赖列出来，转给新部门的要逐项勾选。

### 3.4 校验

校验都在申请全部应用后统一进行，并检查整个期间，不只看今天：

- 退出部门在 T 及以后没有在用单元、下级部门，也没有未结束的编码解释；
- 每个参与部门的版本在 T 前后衔接正确：新设部门自 T 起正式履职；
- 演变关系不是行政上下级，A → B → A 是允许的，不按成环处理。

### 3.5 展示

- 部门详情加“沿革”一节，复用拆分、合并图示（`EvolveFlow`），写明依据与承接范围。
- 申请页按事件显示同一张图，下面列出承接清单。
- 导出增加 `department-lineage` 数据集。

### 3.6 验收剧本（拟新增）

- **剧本 18 整体拆分**：按意见中的呼吸内科示例（模拟数据），走完单元改挂、子部门改挂、旧部门代码结束、新部门分类确认，检查历史日期仍查得到原部门。
- **剧本 19 分设**：原部门存续并改名，新设部门承接部分单元；原部门仍为正式履职，代码和历史都不变。
- **剧本 20 吸收合并**：A 并入 B；B 身份不变，A 的单元改挂 B，A 被替代。

另在 `test_rules` 里补反例：

- 依赖没处置就不能确认；
- 不能手工把部门改为“被替代”；
- 不能直接把旧代码改指向新部门。

### 3.7 工作量估计

| 部分 | 内容 |
| --- | --- |
| 迁移 0011 | 两张表、确认规则 |
| 后端 | 变更项 `department.reorganize`、依赖查询、校验、三条剧本测试 |
| 前端 | 向导（身份裁决 → 参与部门 → 承接清单 → 图示核对），沿革展示 |

总体比服务单元拆分、合并大一倍左右。

## 4. 第二期：规划好，以后做

- **身份纠错（重复数据归并）**：单独的事件类型。被纠错的记录不算“退出”，它的历史解释要并到存续身份上。查询沿革时不能把它显示成组织撤并。
- **结构化的承接范围**：第一期用文字说明承接了哪些职责；以后可改为职责条目，与“承担职责”标签对应。
- **分范围、分批生效**：第一期用多个事件分别表达。
- **实施与核验回执**：对接下游系统后，按“哪个系统、执行了什么、结果如何、还剩什么”记录，并支持未完成项提醒。
- **服务单元的多种责任关系**：运营主责、临床服务责任、专业管理、使用关系分开表达。现在的“所属部门”就是运营主责。

## 5. 不在本平台范围（只在事件里登记待办）

以下对象不在本平台里：

- 人员任职；
- 临床授权；
- 医保资格与账号权限；
- 在途医疗单据；
- 成本、预算、绩效清算。

第一期在组织变更事件里提供一份“需其他系统办理的事项”文字清单，提醒责任方，但不执行、不追踪。历史收入、病案等的归属一律不改，组织承接也不折算为统计或财务比例。

## 6. 需要 Peter 确认

1. 第一期的范围（第 3 节）和四种事件类型、名称是否合适。
2. 组织变更事件的“正式依据”是否必填。建议必填，填文件号或决定说明，不校验。
3. 指向退出部门的外部编码解释是否默认结束（之后进入“待裁决”）。
4. `SUPERSEDED` 是否只能由组织变更事件产生，不能手工改。
5. 时间粒度保持现有约定：按日期、起止都含当日。意见里的“左闭右开、零时生效”，按日期理解时与现有约定等价。
