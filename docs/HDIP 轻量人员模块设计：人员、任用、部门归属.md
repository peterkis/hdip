# HDIP 轻量人员模块设计：人员、任用、部门归属

草案 v0.1 · 2026-10-21 · 依据：组织模块现状（提交 167f36c）、`docs/refer/HDIP-Personnel-MVP-Implementation-Plan-v1.0-20261021.md`（下称“实施计划”）、`docs/refer/CONTEXT.md`“人员与任职”、院方资料包“科室人员多视图应用例与责任边界”，以及 2026-10-21 Peter 的两轮决定（第 1、13 节）。

本文件与组织模块的设计文档（`docs/HDIP 轻量 MVP 设计：主体、院区、服务单元维护.md`，下称“组织设计”）同一写法：只定对象、规则、动作、页面和验收剧本。两份冲突时，人员相关以本文件为准，通用机制（申请流、日期、代码、历史保护）以组织设计为准。

## 1. 目标与边界

**目标**：维护人员不靠开发者改库，就能把一个人登记进来、建立任用和主部门，经提交确认后生效；之后能更名、调科、结束任用、再次任用；并能按任意日期查到当时这个人在哪个主体任用、归属哪个部门，导出名册。

**业务主线**：查有没有这个人 → 新建或选中这个人 → 任用 + 主部门 → 保存草稿 → 提交 → 确认 → 按日期查询 → 调科 / 结束 / 再次任用 → 回查历史。只有整条线走通，人员首版（P1）才算完成；只有表和名册不算。

**范围内（P1）**：人员、任用、部门归属（只有“主归属”）；组织退出时的人员依赖保护。

**范围外**（某条剧本因它失败时才引入）：证件号、性别、出生日期、私人联系方式、银行卡；职称、岗位、编制、职级；执业资格、执业注册、临床授权、处方权；排班、轮转计划、考勤、薪酬；平台账号与权限（人员 ≠ `app_user`）；来源名单导入（P2）；附加归属、负责人（P3）；双时态、发布与投递、人员合并。

**已确认决策**

| # | 决策 |
| --- | --- |
| P-1 | 三个业务对象：人员（这个自然人是谁）、任用（与哪个主体是什么关系、什么期间）、部门归属（这项任用下何时归属哪个部门）。人员上不存“当前部门”，也不存“在职 / 离职”状态 |
| P-2 | 更名、调科、跨院区、离院、返聘都保留同一个人员身份和代码；返聘 = 同一人员新建一项任用 |
| P-3 | 任用结束日可以在登记时就填（医院一般提前填写），不填 = 长期有效。**结束日未到达前可以修改**（提前、推后、清空）；到达后不能再改，也不支持“接续”，一律走再次任用（新任用 id）（2026-10-21 Peter） |
| P-4 | 任用类型启用一组常见码值：在编、合同（人事代理）、劳务派遣、退休返聘、外聘专家、规培、进修、实习（2026-10-21 Peter）。码值放 `option_item`，可加不可重释 |
| P-5 | **两种号分开**：人员代码（P+6，系统生成，规则保证唯一，永不变）≠ 业务工号（人事系统发的号，会变：如实习时一个号，转正后人事换发另一个号）。业务工号 P1 可选录入，**带期间、挂在任用上**，换号 = 旧号止于 D−1、新号自 D 起；按字符串原样保存（`0007` 不丢前导零）；**同一主体内一个工号永远只属于一个人**：离开后不再发给别人，本人返聘可沿用原号（数据库排他约束）（2026-10-21 Peter） |
| P-11 | 姓名改动分两种并分别标记：**更名**（本人改名，旧名是曾用名，可检索）与**更正**（录入错误，旧值标“误录”）。两种都自生效日起产生新版本，P1 不改写已生效的历史（2026-10-21 Peter） |
| P-12 | 谁能改人员数据：P1 沿用组织模块的角色与确认规则；但人员模块的可见、发起、确认、敏感字段都按**独立的权限键**判断，以后细分权限只改映射，不改业务代码（第 8 节）（2026-10-21 Peter） |
| P-13 | 试点任用主体只有成都市第三人民医院一个（2026-10-21 Peter）。表单默认带出、不让人选；模型仍保留主体字段，以后多主体时不改表 |
| P-6 | 部门处于“筹备”或“暂停履职”时，可以有人员归属，只提示不阻止；归属期间不能落在部门开始之前，也不能落在部门撤销、被替代之后（2026-10-21 Peter）。这比服务单元“全期须正式履职”宽：行政归属与单元可运行期间是两回事 |
| P-7 | 人员代码由系统分配：`P` + 6 位数字（如 `P000001`），沿用院区 / 部门 / 单元的预留与不复用机制；这是平台管理代码，不是医院工号 |
| P-8 | P1 每项任用同一天最多一条主归属，允许“暂未分配”（须在表单里明确选择）；同一人员与同一主体的任用期间不重叠——目前两个新院区尚无业务，没有并行任用；以后可能出现，所以这只是一条**可撤掉的约束**（删一个排他约束即可），主归属唯一性按任用而不是按人员计，模型不需改。不得为绕过它重复建人（2026-10-21 Peter） |
| P-9 | 写入只经变更申请，复用现有草稿、提交、确认、退回、撤销、复制；人员相关变更项与组织变更项可以放在同一张申请里 |
| P-10 | 部门撤销、被替代时，依赖它的人员归属（含未来才开始的）阻止确认并列出，在同一张申请里明确改挂或结束；不按服务单元或名称自动迁人。部门更名、调整隶属、服务单元改挂都不迁人 |

## 2. 硬约束与日期规则

组织设计的三条硬约束原样适用，人员这里的含义：

1. **身份与代码**：人员 id 永不复用；人员代码全局唯一、永久绑定，人员“离院”后也不释放。姓名不唯一，同名可共存，系统不按姓名、工号合并人员。
2. **不覆盖历史**：姓名改动产生新版本行；调科 = 结束旧归属 + 新建归属；无物理删除。**唯一的放宽**见第 3.3 节：任用、归属的结束日在到达前可以改（P-3），这是本模块专用的保护函数，不改组织表的“结束日只写一次”。
3. **语义边界**：人员 ≠ 系统账号；任用有效 ≠ 允许执业；部门归属 ≠ 服务单元安置 ≠ 排班。页面不显示“已具备执业资格”“离院处置已完成”这类话。

**日期**（闭区间，起止都含当日；结束日为空 = 长期有效）

| 动作 | 结果 |
| --- | --- |
| D 日调科 | 旧归属最后有效日 D−1，新归属自 D 起；人员、任用不变 |
| 结束任用，最后有效日 E | E 当天仍有效，E+1 起无此任用；归属随之处理（第 5.4 节） |
| 计划生效 | 开始日晚于今天的任用 / 归属显示“计划中”，当天人数不计；到日即生效，不需要定时任务 |
| 撤销计划 | 尚未开始的任用 / 归属，结束日写成开始日前一日（空期间，从未生效，记录保留，沿用 `apply.is_void`），页面写“生效前已撤销” |
| 更名 / 更正姓名 | 新姓名版本自生效日起；旧日期查到旧姓名（更正时旧姓名旁标“误录，已于 X 更正”） |
| D 日换工号 | 旧工号止于 D−1，新工号自 D 起；人员代码、任用不变 |

**人员的开始日**：人员第一个姓名版本的开始日 = 登记向导里首项任用的开始日（表单自动带上）。任用开始日不能早于人员开始日，表单提示“人员档案自 X 起，任用不能更早”。

## 3. 数据模型

```
主体 ──┐
       ├── 任用（人员 × 主体 × 类型 × 期间）
人员 ──┘          ├── 业务工号（任用 × 工号 × 期间，可换号）
                  └── 部门归属（任用 × 部门 × 期间，P1 只有 PRIMARY）
部门 ─────────────┘
```

### 3.1 五张业务表

| 表 | 作用 | 历史策略 |
| --- | --- | --- |
| `person` | 身份：id、code（P+6）、创建申请与时间（同 `_Identity`） | 不改不删 |
| `person_version` | 姓名版本：name、pinyin、`revise_reason`（`INITIAL` 登记 / `RENAME` 更名 / `CORRECTION` 更正误录）、version_no、期间、申请、记录人与时间（同 `_Version`） | 同其他版本表：只能把结束日从空写成某日；未生效的最新版本可在开始日当天更正 |
| `person_engagement` | 任用：person_id、institution_id、engagement_type、note（可空）、期间、申请、`closed_change_id`（同 `_Period`） | 端点、类型、开始日不可改；结束日到达前可改（3.3） |
| `person_work_no` | 业务工号：engagement_id、person_id 与 institution_id（随任用复制，供排他约束用，不可改）、work_no（text）、`revise_reason`（`INITIAL` / `CHANGE` 换号 / `CORRECTION` 更正误录）、期间、申请、`closed_change_id` | 同任用 |
| `person_assignment` | 部门归属：engagement_id、department_id、kind（P1 只 `PRIMARY`）、期间、申请、`closed_change_id` | 同任用 |

- **为什么工号单独成表**：工号会在同一任用里变（实习转正换号），也会随新任用变；挂在任用行上就只能改写或重建任用，两样都不对。单独带期间，回查“某日此人用哪个工号”、按旧工号查人都自然成立。
- **曾用名与误录的区别只用 `revise_reason` 表达**，不另建表：某版本的下一版本是 `CORRECTION`，它的姓名就是“误录”；是 `RENAME`，它的姓名就是“曾用名”。工号同理。

- 任用、归属不另设人工维护的编号，页面用“人员 + 主体 + 部门 + 日期”表达，变更项内部用行 id（与运营关系一致）。
- `closed_change_id` 在这两张表上的含义是“最近一次写入或调整结束日的申请”；每次调整的原结束日、新结束日都在该申请的变更项前后内容里（JSONB），详情页从申请里还原“结束日调整记录”，不另建日志表。
- 配置种子（`option_item`）：
  - `engagement_type`：`STAFF` 在编、`CONTRACT` 合同（人事代理）、`DISPATCH` 劳务派遣、`REHIRE` 退休返聘、`EXTERNAL` 外聘专家、`RESIDENT` 规培、`VISITING` 进修、`INTERN` 实习。
  - `assignment_kind`：`PRIMARY` 主归属（P3 再加 `ADDITIONAL` 附加归属）。
  - `person_relation_status`（只用于显示与导出，不存储）：`ENGAGED` 有有效任用、`PLANNED` 仅有计划任用、`NONE` 无有效任用。

### 3.2 约束（数据库层，显式命名并补 `CONSTRAINT_MESSAGES` 中文翻译）

| 名称 | 约束 |
| --- | --- |
| `person_code_key` | 人员代码唯一；`code ~ '^P[0-9]{6}$'` |
| `person_version_no_overlap` | 同一人员姓名版本期间不重叠（半开区间写法，与 0011 一致，空期间不参与） |
| `person_engagement_no_overlap` | 同一人员 + 同一主体的任用期间不重叠（P-8；以后允许并行任用时删掉这一条） |
| `person_work_no_no_overlap` | 同一任用的工号期间不重叠（同一时点一个工号） |
| `person_work_no_one_owner` | 同一主体、同一工号只能属于同一个人，不论期间：`EXCLUDE USING gist (institution_id WITH =, work_no WITH =, person_id WITH <>)`（`btree_gist` 已启用）。本人返聘沿用原号可以；发给别人被拒。工号的格式不校验（医院规则未给） |
| `person_assignment_primary_no_overlap` | 同一任用的 `PRIMARY` 归属期间不重叠（`EXCLUDE ... WHERE (kind = 'PRIMARY')`）。不按部门分桶，否则会放过两个主部门 |
| `*_period_check` | `valid_to IS NULL OR valid_to >= valid_from - 1`（允许空期间） |
| 外键 | engagement → person、institution；assignment → engagement、department；类型码由应用层查 `option_item` |

跨表规则在申请**全部变更项应用后**统一检查（新增 `apply.py` 的 `_check_persons`，与 `_check_units` 同形）：

- 任用开始日不早于人员开始日、不早于主体开始日。
- 每条归属、每段工号的**完整期间**落在所属任用期间内。
- 每条归属的完整期间内，部门已开始存在，且没有“撤销 / 被替代”段（P-6）；与“筹备 / 暂停履职”段相交时只提示。
- 被本申请改动过的部门（改生命周期、组织变更）——它的**全部**归属（含未来才开始的）都重查一遍。这样“单元今天在 A、预约明天改到 B，B 提前退出”这类未来流入，在人员这边不会漏。

### 3.3 历史保护：结束日在到达前可改

现有 `hdip_guard_update` 规定结束日只能从空写成某日一次，之后整行不可改（迁移 0003）。人员任用、工号、归属需要“结束日未到前可改”（P-3），所以**新写一个只给这三张表用的保护函数**，组织表保持不变：

```
hdip_guard_open_end()  -- 用于 person_engagement、person_work_no、person_assignment
  - 只有 valid_to、closed_change_id 两列可改，其余列（端点、类型、工号值、开始日）一律不可改
  - 原结束日已过去（OLD.valid_to < current_date）→ 整行不可再改
  - 原行是空期间（OLD.valid_to = OLD.valid_from - 1，即已撤销的计划）→ 整行不可再改
  - valid_to 改动时 closed_change_id 必须同时写成本次申请（不同于原值）
```

- `current_date` 取会话时区（`HDIP_TIMEZONE`），与应用的“今天”一致。
- 新的结束日可以早于今天（迟报的离院、调科照样能登记），但只能改“还没到”的结束日。
- `person`、`person_version` 用现有 `hdip_guard_update`。
- 测试里涉及“未到 / 已到”的用例按 `date.today()` 推算日期，不写死年份。

### 3.4 并发

两张申请同时确认（例如“撤销部门 B”与“把某人调入 B”）可能各自通过最终检查。确认时在事务开头取一个全局事务级咨询锁（`pg_advisory_xact_lock`），所有确认串行执行；确认本来就是低频动作，代价可忽略。组织模块同样受益。

结束日调整、调科、结束归属都带“预期原结束日”（`expected_valid_to`）；确认时与库里不一致就拒绝：“这条任用的结束日已被申请 #N 改为 X，请刷新后重做”。草稿不会悄悄覆盖别人已确认的结果。

## 4. 变更项

对象之间用 code 引用（人员、主体、部门），任用和归属用 id（与运营关系一致）。所以登记向导在同一张草稿里先 `person.create` 再 `person.engage`，后一项按代码引用前一项新建的人员。

| kind | 字段 | 结果 |
| --- | --- | --- |
| `person.create` | code（预留）、name、pinyin?、valid_from | 新人员身份 + 第一个姓名版本 |
| `person.revise` | code、reason（`RENAME` / `CORRECTION`）、valid_from、name?、pinyin? | 新姓名版本（同部门修订规则：只作用于最新版本；未生效的最新版本可在开始日当天更正；内容无变化被拒） |
| `person.engage` | person_code、institution_code、engagement_type、work_no?、note?、valid_from、valid_to?、department_code? | 新任用 + 同期间的工号（若填）与主归属；`department_code` 为空 = 暂未分配（表单须明确选择）。返聘也用它 |
| `person.change_work_no` | engagement_id、expected_work_no、reason（`CHANGE` / `CORRECTION`）、work_no（空 = 此后不再有工号）、effective_date | 旧工号止于 D−1，新工号自 D 起；任用原本没有工号时直接新建一段 |
| `person.engagement_set_end` | engagement_id、expected_valid_to、valid_to（空 = 清除结束日）、extend_assignments（默认是） | 结束任用 / 调整结束日 / 撤回结束日 / 撤销计划，并处理所属归属（5.4） |
| `person.transfer` | assignment_id、expected_valid_to、department_code、effective_date | 调科：旧归属止于 D−1，新归属自 D 起、结束日沿用旧归属的结束日 |
| `person.assign` | engagement_id、department_code、valid_from、valid_to? | 给“暂未分配”的期间补主归属 |
| `person.assignment_set_end` | assignment_id、expected_valid_to、valid_to | 结束 / 调整一条归属（之后为暂未分配），或撤销未开始的归属 |

共 8 个 kind。

新增一种变更 = schema + `HANDLERS` + `approval_rule` 种子 + `describe.py` 的一句话与 `item_views` + 测试（组织设计第 4 节的既有做法）。`approval_rule` 必须为全部 8 个 kind 显式写种子（默认：维护人提交、确认人确认、允许自确认），不依赖“缺规则就放行”的默认分支。

**代码预留**：`services/codes.py` 的 `RULES` 加 `"person": ("P", 6, "person_code_seq", "人员")`；`workflow.created_codes` 识别 `person.create`；`apply._require_issued` 检查人员代码已预留；“复制为新草稿”沿用已预留的代码。

## 5. 动作与校验

问题提示沿用 `ItemError(message, field, hint=..., facts=[...])` 写法（短句、先事实后操作、用名称不用 id）。下表“拒绝”列是会出现的典型提示。

### 5.1 登记新人员（向导：查重 → 姓名 → 任用与主部门）

- **先查重**：按姓名 / 拼音码 / 人员代码 / 工号检索**全部**人员，含历史、未来、无有效任用的人；结果显示代码、各项任用（主体、类型、期间、工号）和当时主部门。操作员可以选“就是此人”（转去再次任用）或“同名不同人，继续登记”。
- 生成两项：`person.create` + `person.engage`；人员开始日 = 任用开始日。
- 拒绝：主部门在开始日之前尚未设立；主部门已撤销；主体不存在。
- 拒绝：工号 `0007` 已属于“张三（P000003）”（同一主体内工号不复用，离开后也不发给别人）。
- 提示（不阻止）：同名人员已存在 N 位；主部门在此期间有筹备 / 暂停履职段。

“提示”是本模块新增的非阻止信息：预演结果里与问题（problems）并列返回 `notices`，申请页在对应变更项下显示，不影响提交与确认。

### 5.2 姓名：更名与更正

表单先问“为什么改”，两个选项对应两种业务事实（P-11）：

| | 更名（本人改名） | 更正（录入错误） |
| --- | --- | --- |
| 生效日 | 改名的实际日期，可以是过去、今天或将来 | 默认今天，可填过去（不早于误录版本的开始日之后一天） |
| 旧日期查询 | 显示旧姓名 | 显示误录的姓名，旁注“误录，已于 X 更正为 Y” |
| 检索 | 旧名作为**曾用名**可检索 | 误录值仍可检索（以防有人按错名找），结果标“误录” |
| 导出 | 按日期取当时姓名 | 同左（P1 不回改历史） |

- 若最新版本尚未生效（例如登记了下月入职的人），在开始日当天修订 = 直接替换，不留误录期间（沿用 0011 的空期间更正）。
- 已生效的姓名，P1 不改写历史，只自生效日起改正；若误录更正频繁，再加“历史更正”动作（需定谁能做、原值怎样留证）。

### 5.2a 工号：换号与更正

- 换号（实习转正、人事系统改号）：选任用 → 新工号 → 生效日 D；旧号止于 D−1。人员代码不变，旧工号仍可检索到此人。
- 更正误录的工号：同一动作，原因选“更正”，生效日默认今天；旧值标“误录”。
- 实习结束后以合同或在编身份重新任用，通常是新任用（类型变了），新工号在新任用里登记；实习任用和旧工号保留。
- 拒绝：新工号已属于（或曾属于）同一主体的另一人。

### 5.3 调科

- 选本次任用当前（或计划中的）主归属 → 目标部门 → 生效日 D。预览 D−1、D 两天分别归属哪个部门。
- D 必须晚于旧归属开始日。D 等于旧归属开始日、且旧归属尚未开始 → 自动按“撤销旧计划 + 新建”处理（空期间），提示写清楚；D 等于开始日但旧归属已生效 → 拒绝：“这条归属已于 X 生效，调科日须晚于 X”。
- 新归属的结束日沿用旧归属的结束日；该任用后续已确认的计划归属不动。
- 拒绝：目标部门与原部门相同；目标部门在 D 尚未设立或已撤销；新归属越出任用期间。

### 5.4 结束任用、调整结束日、撤销计划（同一个动作）

| 情形 | 页面用语 | 归属的处理（自动，预演里逐条列出） |
| --- | --- | --- |
| 原结束日为空，写 E | 结束任用 | 开始日 ≤ E 且结束日晚于 E（或为空）的归属、工号段，结束于 E；开始日 > E 的计划归属撤销（空期间）；已在 E 前结束的不动 |
| 原结束日 > 今天，改为更早的 E′ | 提前结束 | 同上，以 E′ 为界 |
| 原结束日 ≥ 今天，改为更晚或清空 | 推后 / 撤回结束日 | 结束日恰好等于原结束日的归属，按 `extend_assignments`（默认是）一并推后 / 清空；其他归属不动 |
| 任用尚未开始，写开始日前一日 | 撤销计划 | 该任用下全部归属一并撤销 |
| 原结束日已过去 | — | 拒绝：“这项任用已于 X 结束，结束日不能再改。如再次任用，请在人员详情点‘再次任用’” |

- 归属、工号是任用的下属，随任用一起处理（同部门撤销时自动结束自己的上级边）；这与部门退出不同——部门的人员不归部门“所有”，须人逐条处置（第 6 节）。
- 同一人其他主体的任用不受影响。
- 结束任用只表示“本次任用关系已结束”，页面不写“离院处置完成”。

### 5.5 再次任用（返聘）

- 从人员详情点“再次任用”：选中原人员，生成一项 `person.engage`（新任用 id，可带新工号、新类型）；旧任用原样保留。
- 拒绝：与此人在同一主体的另一项任用期间重叠（P-8）——提示：“张三在本院的任用 2018-07-01 至 2026-12-31 仍有效，新任用须从 2027-01-01 起”。

### 5.6 补归属、结束归属

- `person.assign`：给暂未分配的期间补主归属。拒绝：与已有主归属重叠（“该任用 2027-01-01 起已归属心内科”）。
- `person.assignment_set_end`：结束后此任用为“暂未分配”，页面标黄提示。

## 6. 与组织模块的联动

从第一条人员归属可以确认那天起，下面的保护必须同时生效（P1.1 的一部分，不是后补）。

| 组织动作 | 对人员的影响 |
| --- | --- |
| 部门更名、改简称、调整行政上级、改主分类 | 不迁人；历史名称按日期解释 |
| 部门改为暂停履职 | 不阻止；人员详情和部门“人员”区块显示“部门暂停履职”提示；不自动结束任用 |
| 部门撤销（`change_lifecycle` → REVOKED） | 自退出日起仍有归属（含未来才开始的）→ 阻止确认，列出人员、归属起止、当前 / 计划；在同一张申请里调科或结束归属后才能确认 |
| 部门被替代（`department.reorganize`） | 同上；组织变更向导在“承接”步骤增加“人员”清单：每条选“调到承接部门（D 起）”或“结束归属（D−1 止）”，生成 `person.transfer` / `person.assignment_set_end`；新设部门在同一张申请里新建，按代码引用 |
| 服务单元改挂部门、改院区、拆分合并 | 不改变任何人员归属 |

**影响清单的口径**：与退出日 D 及以后**相交**的全部归属（`valid_to IS NULL OR valid_to >= D`，含 `valid_from > D` 的计划），不是 D 当天的快照。`queries.department_dependencies` 增加 `persons` 一栏，按此口径查询。

服务单元一栏已于 2026-10-21 改为同一口径（`queries._units_from`，第 14 节）；人员一栏照此实现。

## 7. 查询、页面与导出

### 7.1 接口（只读，`operation_id` 决定 hook 名）

| 接口 | 用途 |
| --- | --- |
| `GET /api/persons?as_of=&q=&institution=&department=&status=&include_future=` | 名册：每人一行；`status` 按查看日期派生（有效任用 / 计划 / 无） |
| `GET /api/persons?scope=all&q=` | 查重：不受查看日期限制，含历史、未来、无有效任用的人；姓名、曾用名、误录名、拼音码、人员代码、**现用与历史工号**都能命中，结果写明命中的是哪一项（如“旧工号 S2019001，2019-07-01 至 2022-06-30”） |
| `GET /api/persons/{id}?as_of=` | 详情：身份、当日姓名、姓名版本（标更名 / 更正）、任用（含下属工号段与归属）、相关申请、结束日调整记录 |
| `GET /api/departments/{id}/persons?as_of=` | 部门“人员”区块：该日直属主归属人员（不含下级部门） |
| `GET /api/departments/{id}/dependencies?day=` | 现有承接清单，加 `persons` |

### 7.2 页面（按 Notion 风格与现有 kit 组件）

- **导航**：“人员、资质与任职”组里，“人员与身份”“聘用与合作关系”两个规划条目合并为已实现的“人员名册”（`/persons`）；“岗位与任职”“执业资质”“临床授权”仍是规划中。
- **人员名册**（`kit/database`）：检索框（姓名 / 拼音码 / 代码 / 工号）；主体、部门、状态筛选；“含计划”开关；表头写明查看日期；右上“登记人员”“导出”。人数 = 当日有效任用下按人去重。
- **人员详情**：PageHeader（姓名、代码、状态 Tag）；PropertyList（当日主体、类型、工号、主部门；曾用名）；“任用与归属”用竖向时间线（`version-timeline.tsx`）按任用分段画出归属与换号；每项任用旁的轻量操作：调科、换工号、结束 / 调整结束日、补归属；页头操作：改姓名（先选更名 / 更正）、再次任用。
- **登记向导**（弹窗，三步，`kit/steps`）：①查重 ②姓名（拼音码可改）③任用与主部门（主体只有一个时直接带出、不显示选择；类型；开始日；结束日选填；工号选填；主部门按名称下拉，或明确选“暂未分配”）→ 保存到申请。
- **部门详情**：新增“人员”区块，列当日直属人员（姓名、任用类型、归属起止），计数与名册同口径。
- **申请页**：`item_views` 按“主语 → 谓语 → 宾语”：“张三（P000001）调到 心内科，自 2027-01-01 起；原 神经内科 止于 2026-12-31”。结束任用一行下面列出被一起处理的归属。
- **拼音码**：人名首字按姓氏读音（pinyin-pro 的姓氏模式：单 Shan、曾 Zeng、解 Xie、仇 Qiu、区 Ou），**`lib/pinyin.ts` 的 FIXED（区 → Q）只用于组织名称，不用于人名**；多音字照常提示核对。后端 pypinyin 没有姓氏模式，所以人员的拼音码以前端提交为准，后端只在缺失时兜底。

### 7.3 导出（`services/export.py`，UTF-8 BOM，列名英文，码值另附中文名列，新增列只加在末尾）

| 数据集 | 一行是 | 列 |
| --- | --- | --- |
| `persons` | 一个人（该日有姓名版本的人） | person_code, name, pinyin, relation_status, relation_status_name |

`work_no` 取该日有效的工号段。以后加入的敏感字段按第 8 节处理：无权限则导出空值，列不删，契约不变。
| `person_relations` | 该日有效的一项任用 × 当日主归属（暂未分配时部门列为空） | person_code, name, institution_code, institution_name, engagement_type, engagement_type_name, work_no, engagement_valid_from, engagement_valid_to, assignment_kind, assignment_kind_name, department_code, department_name, assignment_valid_from, assignment_valid_to |

“暂无主归属”不写成“离职”；“任用有效”不写成“可执业”。

## 8. 权限与敏感信息（P1 预留，后续细分）

现状：`core/permissions.py` 已把“角色 → 权限键”集中在一处，调用处只问权限键；确认权限由 `approval_rule` 按变更类型配置。人员模块在此之上**只加权限键和检查点**，P1 的映射与组织模块等价（P-12），以后细分只改映射（再往后换成 `role_permission` 表），不改业务代码。

### 8.1 权限键

| 权限键 | 含义 | P1 映射 |
| --- | --- | --- |
| `person.view` | 看到人员模块：导航、名册、详情、部门“人员”区块、含人员变更项的申请 | 全部现有角色 |
| `person.view_sensitive` | 看到敏感字段（第 8.2 节）：身份证号、联系电话等 | 全部现有角色（P1 尚无敏感字段） |
| `person.export` | 导出人员数据集 | 全部现有角色 |
| `person.change` | 发起、编辑、提交含人员变更项的申请（代码预留同样检查） | 维护人 |
| 确认 / 退回 | 仍由 `approval_rule` 按 kind 配置确认角色与是否可自确认 | 确认人；允许自确认 |

你说的几类人，都能只靠映射表达：只能看（`person.view`）、能改能提交（+ `person.change`）、能审核（`approval_rule` 的确认角色）、全能（都有）、看不到人员模块（没有 `person.view`）、看不到敏感信息（没有 `person.view_sensitive`）。

### 8.2 敏感字段：后端统一脱敏

- 在 `schemas/read.py` 旁建一张**字段 → 所需权限键**的登记表（`PERSON_FIELD_PERMISSIONS`，P1 为空；以后加身份证号时写 `{"id_card_no": "person.view_sensitive", "phone": "person.view_sensitive"}`），读接口、导出、申请页的 `item_views` / 一句话说明**都从同一处**按当前用户脱敏：值置空，响应里带 `masked_fields` 列出被隐去的字段，前端显示“无权查看”。
- 只在后端判断，前端只按 `/api/meta` 返回的权限键决定显示哪些入口，不承担保密。
- 工号不是敏感字段（2026-10-21 Peter）。敏感字段主要是身份证号、联系电话，P1 不采集，所以登记表为空；但脱敏函数、`masked_fields` 与测试（用测试里临时登记的字段）在 P1.1 就做好，加字段时只加一行登记，不改接口形状。
- 没有 `person.view` 的人：导航不显示人员组；人员接口返回 403；申请列表里含人员变更项的申请**整张隐藏**，按号打开返回 404（2026-10-21 Peter）；部门详情不显示“人员”区块。
- 现在是开发期身份（`X-HDIP-User`），这些检查只防误用、不防冒用；真实数据上线前须先完成第 12 节的身份认证。

| --- | --- | --- |

| **P1.2 变化与历史** | `person.revise`（更名 / 更正）、`person.change_work_no`、`person.transfer`、`person.assign`、`person.assignment_set_end`；预演 `notices`；`expected_valid_to` 并发拒绝 | PERS-03、04、09 |

P1 停止条件：PERS-01～09 通过，一名维护人员不改库走完主线。到此停止加字段。P2、P3 互不为前置，负责人更急就先做 P3。

### 10.1 P3 部门职务预案（按院内实际，2026-10-21 Peter 提供）

院内现状：部门有部长（正）、副部长；有代理部长、代理副部长，代理部长院内叫“主持工作”；也有一位部长同时临时管理两个部门（如既管医务部、又代管院感部）。

由此定下与实施计划不同的一点：**职务挂在“任用 × 部门”上，不挂在部门归属上**。代管的部门不是此人的归属部门（乙的主归属仍是医务部，不能为了代管院感部给他再建一条归属），所以职务只要求落在任用期间内，不要求此人归属于该部门。

| 项 | 预案 |
| --- | --- |
| 表 | `person_duty`：engagement_id、department_id、duty（`HEAD` 部长 / `DEPUTY` 副部长，`option_item`，以后可加护士长等）、mode（`FORMAL` 正式 / `ACTING` 代理（主持工作）/ `CARETAKER` 代管）、期间、申请；保护同 `hdip_guard_open_end` |
| 约束 | 同一部门同一天：正式部长（`HEAD FORMAL`）最多一位；主持工作者（`HEAD ACTING` 或 `HEAD CARETAKER`）最多一位；两者**可以并存**——部长外出学习、派驻其他医院期间，由他人主持工作（2026-10-21 Peter）。`DEPUTY` 不限人数；同一人同一部门同一 duty 不重叠。“副部长（主持工作）”= 同一人一条 `DEPUTY FORMAL` + 一条 `HEAD ACTING` |
| 期间 | 落在任用期间内；落在部门存在、未撤销 / 被替代的期间内 |
| 联动 | 任用结束 → 职务随之结束（同归属）；部门撤销 / 被替代 → 该部门的职务自动结束于 D−1 并在预演中列出（职务依附部门存在，与部门关系同样处理）；调科不带走职务 |
| 显示 | 部门详情按查看日期派生“负责人”：有主持工作者时显示主持工作者，并注明“部长：甲”；没有时显示部长；代管标“代管”。部门版本里不存姓名 |
| 期限 | 代理、代管都不强制结束日（2026-10-21 Peter） |
| 动作 | `person.duty_assign`、`person.duty_set_end`、`person.duty_handover`（甲止于 D−1、乙自 D 起，一项完成） |
| 权限 | 职务不等于系统权限，不自动授予任何 `app_user` 角色 |

P3 启动前还要确认：主持工作（代理）与代管在院内是否需要区分（预案分开记录，显示上都算“主持工作”）。

## 12. 真实人员数据的上线门槛

开发与走查可以立即用合成数据。导入真实人员名册、向日常用户开放之前，至少要：

1. **服务端验证身份**：替换 `core/auth.py` 的 `X-HDIP-User` 开发身份（接入内网门户，或最小本地登录 + 会话）。只替换 `core/auth.py` 与 `web/src/lib/session.ts`，不建 IAM 平台。
2. **权限真正生效**：人员读取、导出需要登录；维护、确认按现有角色与 `approval_rule`。
3. **字段只收 P1 需要的**：姓名、拼音码、任用、工号、部门；不借机收证件和私人联系方式。
4. **小样本实地核对**：少量真实记录对照主体、部门、生效日、人数走一遍，记录仍不支持的例外。
