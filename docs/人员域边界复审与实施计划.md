# 人员域边界复审与轻量实施计划

2026-10-24 · 依据：`docs/refer/HDIP-Personnel-Master-Data-Scope-and-Agent-Plan-v2.0-20261024.md`（下称“v2.0”）、现有人员设计（`docs/HDIP 轻量人员模块设计：人员、任用、部门归属.md`）、代码现状（HEAD `a7eed63`），以及 2026-10-24 Peter 的四项决定（第 2 节）。

本文是对 v2.0 的中立复审和可执行的轻量计划：采纳 v2.0 的主体边界，按本院实际收窄 A1、调整命名，并按已确认的真实用途排定 A1 之后的顺序。本文**不代表功能已实现**；每个阶段完成后在人员设计第 10.3 节“完成情况”里分列代码、自动化、浏览器走查。

## 1. 复审结论

**v2.0 的主体边界合理，采纳；有五处按本院实际调整。**

### 1.1 采纳的判断

| # | v2.0 的判断 | 复审意见 |
| --- | --- | --- |
| 1 | HDIP 是人员身份与组织关系的共享目录，不承办 HR、资质、临床授权业务 | 合理。与“其他系统已有的业务不在本平台重复建设”一致；平台登记已确定的结果，不复制审批过程 |
| 2 | 临床授权退出当前开发路线 | 合理。手术等授权须经医疗机构评估、批准、动态调整（国卫办医政发〔2022〕18 号），属医务部的医疗治理；日期级手工目录也承担不了实时拦截 |
| 3 | 部门管理任职复用 `person_duty`，菜单改称“部门任职”；HR 岗位、编制、职级不建 | 合理。“岗位”一词覆盖了干部职务、职称、编制岗位、服务角色、系统角色五种不同事物，拆开后只有部门职务属于本平台已有事实 |
| 4 | 跨系统人员身份对应（I1）从导入里拆出、先于导入 | 合理，且是 v2.0 最有价值的修订：与编码映射台账“命名空间 + 源代码”的做法同构；导入只是批量输入方式，同人识别才是基础能力 |
| 5 | 部门 ≠ 工作地点；不从部门的服务单元推断人员在哪个院区工作 | 合理，与组织模块“服务单元 ≠ 地点”的原则一致 |
| 6 | 执业资质只在有消费者时做“来源关联”，不自建证照台账 | 合理。医师 / 护士电子注册与院内资质档案已有权威来源和责任部门 |

### 1.2 调整的五处

1. **A1 收窄（2026-10-24 Peter 选“精简”）**。v2.0 的 A1 新增两套 API、两个 CSV、逐数据集筛选矩阵与 `reference_date`，但它自己的“六问”要求先有消费者，而归属 API / CSV 没有点名消费者。本计划 A1 只做：部门任职台账（全院“各部门负责人是谁”是常见实际需求）、现有导出与页面同口径（页面显示筛选后人数却导出全量，属于正确性问题）、任用延期不自动续职、任职依据。归属 API / CSV 等出现消费者再做。
2. **任职依据部分必填（Peter 选定，调整原决策 3）**。原决策 3：依据只作选填文本、不做依据对象。部门任命通常有院发任命文件，所以**任命、交接必填，结束选填**（结束常因任用结束、部门退出等结构性原因，没有独立文件）；仍是文本，不做附件、不校验文号。旧记录显示“历史记录未提供依据”，不伪造决定人。
3. **任用延期不再自动续职（纠正 P3 的做法）**。P3 实施时“同一天到期的归属与职务一起延长”把职务也带上了。中层干部任期与劳动合同是两条线，延期任用不等于续任职务——采纳 v2.0。只影响今后的申请，不改已确认历史。
4. **导航分组叫“人员与任职”（Peter 选定）**。v2.0 的“人员与组织关系”与现有“组织与关系”分组几乎同名，侧栏里容易混。
5. **A1 之后的顺序按已确认的真实用途排**（Peter 2026-10-24 确认两项近期用途）：
   - **HIS / HR 等系统按平台人员代码对人** → I1 排在 A1 之后第一位。
   - **高新院区开诊后的院区人员派驻** → R1 排第二，须在高新院区试运行前可用。
   - 卫健统计的人员分类暂无近期需求 → 不建“人员类别”。

### 1.3 v2.0 未单列、本计划补上的一项

**服务端身份认证（S0）单列一条线。** v2.0 把它写成条件；但 I1 要接真实人员键、R1 要登记真实派驻，任何真实人员数据进入之前都必须有可信登录（现在是开发期 `X-HDIP-User`）。它与人员域阶段相互独立，可并行，但**是真实数据的硬门槛**。

另：v2.0 的阶段报告模板与契约模板对单人维护的项目偏重，本计划把契约压到一页（`docs/人员共享数据契约.md`），完成情况沿用人员设计第 10.3 节的三列表。

### A1 部门任职台账与共享收尾（不建表）

> **已完成（2026-10-24）**：迁移 0021 只加 `person_duty.basis_note`；`test_a1.py` 覆盖 A1-01～07；浏览器走查见 `docs/剧本走查记录.md`（A1-03 只有后端测试）。实施时的取舍：负责人一览列出当天正式履职的部门及当天有部长职务的部门，只受“任职部门”筛选影响；`person-duties.csv` 与台账同粒度、同筛选；结束职务的依据只留在申请里，不写在职务行上。

| # | 交付 | 要点 |
| --- | --- | --- |
| A1-a | `GET /api/person-duties` + 页面 `/person-duties`（“部门任职”） | 每行一条职务：人员（代码、姓名）、任用主体、**任职部门**、职务与方式、期间、是否计划、依据、创建申请；同时列出此人当天的**主部门**（按任用与查看日期取 `PRIMARY`，代管时两者不同，标清）。返回查看日期、`record_count`、`person_count`（按人员去重）。筛选：`q`、任职部门、职务、方式、含计划。页面复用 `DbTable`（可排序）与现有职务表单；文案为“登记已确定的任命结果” |
| A1-b | 部门负责人一览 | 台账顶部按部门列出当天负责人（与部门详情同一规则：有主持工作者显示主持工作者并注明部长），一眼看出哪些部门空缺 |
| A1-c | `person-duties.csv` | 与台账同日期、同筛选、同粒度；注册到 `PERSON_DATASETS`，需要“导出人员数据”权限 |
| A1-d | 任职依据 `basis_note` | `person.duty_assign`、`person.duty_handover` 必填（1–500 字），`person.duty_set_end` 选填；旧申请 JSON 照常解析，旧草稿重新提交时按新规则补齐；台账与详情显示依据，旧记录显示“历史记录未提供依据” |
| A1-e | 任用延期不自动续职 | `person.engagement_set_end` 推后 / 清空时只延长工号和（可选）归属，不再延长职务；预览与提示写明“职务不随任用延长，续任请另行登记”。缩短、追溯冲突、部门退出的既有保护不变 |
| A1-f | 现有导出与页面同口径 | 名册的“导出名册”“导出任用与归属”带上页面当前的筛选（查询词、主部门、状态、含计划）；该数据集不支持的筛选（如“全部人员”查重视图）时按钮禁用并说明，不悄悄导出全量。既有列名与行粒度不变；`person-relations` 若支持含计划，只在末尾追加 `not_yet_effective` 列 |

### S0 服务端身份认证（独立一条线，真实数据前必须完成）

- 目标：替换开发期 `X-HDIP-User`，让“谁提交、谁确认、谁能看人员”由可信登录决定；只替换 `api/.../core/auth.py` 与 `web/src/lib/session.ts`，角色与权限键沿用。
- 方式待定（第 6 节）：优先接医院现有统一认证入口（门户 / LDAP / CAS 等）；没有时做最小本地账号 + 会话。不建 IAM 产品。
- 时机：I1 接真实人员键、R1 登记真实派驻之前完成；与 A0 / A1 可并行。

### I1 单来源人员身份对应（A1 之后第一位，1 张表）

启动前要拿到（缺一项就不建表，只在契约里记缺项）：

1. 第一个来源系统选哪个：**建议 HR 人事系统**（它的人员键通常代表自然人，且“谁是本院人员”的权威在人事）；HIS 的用户键常代表登录账号或医生执业记录，需先确认是否“一人一键、永不复用”。
2. 该系统的人员键字段、三条以上脱敏样例、是否永不复用、离职后是否回收。
3. 来源维护责任人（部门 / 角色）与第一个消费者（哪个系统、用来做什么）。

交付（按 v2.0 第 9 节，做以下简化）：一张 `person_source_link`（命名空间 + 原样来源键 → 人员；未标误关联的键唯一；业务字段不可改；误关联只能标记一次）；两个动作 `person.source_link_register`、`person.source_link_mark_error`（同一申请里“先标错再登记”即更正）；精确解析接口；人员详情的“来源对应”区块。复用 `source_system` / `code_namespace` 配置。不做导入、不按姓名或工号自动合人、不写回来源。

### R1 院区人员派驻（高新院区试运行前可用，1 张表）

要回答的问题：**某人在什么期间、以什么服务角色、在哪个院区的哪个服务单元工作**。现有的任用、主 / 附加归属、部门职务都回答不了——主部门不等于工作院区，部门在高新院区有服务单元也不等于全科人员都去。

启动前要拿到：

1. 派驻信息的来源与责任方：医务部 / 护理部的派驻安排（排班表不是本平台的事，但“谁被派驻到高新院区哪个单元、自何日起”是稳定的关系事实）。
2. 首轮服务角色码表（建议从来源实际使用的少数几类起步，如医师、护士、医技、药学；不照搬 FHIR 全集）。
3. 第一个消费者（例如高新院区开诊前的人员配置核对、院区通讯录）。

交付（按 v2.0 第 10 节，做一处简化）：一张 `person_service_role`（任用、服务单元、角色、期间、依据）；动作 `person.service_role_register`、`person.service_role_set_end`。**简化**：v2.0 用“锚定服务单元版本 id”防止单元换院区时人员被悄悄迁移；本项目已有同类问题的现成做法——像服务单元依赖部门那样，在申请全部应用后统一检查：单元改院区 / 运营主体、退出、拆并时，仍有当前或未来派驻关系就阻止并列出，由人在同一张申请里处置。这样不需要版本锚点，规则与组织模块一致。单元暂停不结束派驻，但查询标出“单元暂停”。

## 5. 顺序与停止点

```
A0（文档、导航）→ A1（部门任职台账）→ 停
```
