# HDIP 轻量 MVP 设计：主体、院区、服务单元维护

草案 v0.1 · 2026-10-13 · 依据：2026-10-12 统一语言（服务单元）与本轮讨论决策

## 1. 目标与边界

**目标**：维护人员不靠开发者解释，就能独立办完主体、院区、服务单元的新增、调整、停用，并能按任意日期查询当时状态。

**范围内**：主体、院区、主体—院区运营关系、部门、服务单元。部门已深化为部门主数据（D1–D3，见第 13 节）；部门组织变更第一期（拆分、分设、吸收合并、合并新设）已实施，见 `docs/部门组织变更-评估与分期.md`。

**范围外**：审批模板版本、双时态读取、发布快照与消费者投递、证照核验流程、批文/引文/依据机制、病区/护理单元/地点、人员与负责人、层级视图（行政视图除外，见第 13 节）、价表、部门—院区服务关系、部门组织变更第二期（见 `docs/部门组织变更-评估与分期.md`）。这些不是否定，只在某条验收剧本因其失败时才引入。

## 2. 硬约束与日期规则

**三条硬约束**（一旦做错事后无法补救，其余都可后补）：

1. **身份与代码**：id 永不复用；code 永久绑定，对象退出后也不释放。院区、部门、服务单元的代码由系统按规则分配（院区 C + 3 位、部门 D + 6 位、服务单元 SU + 6 位数字，大小写等价；2026-10-19 Peter 决定，见 docs/database/README.md 第 3.1 节），不由人手填。
2. **不覆盖历史**：任何改动都产生新版本行，旧版本保留，无物理删除。
3. **语义边界**：院区不等于法人；服务单元 = 部门 × 院区 × 运营主体 × 期间，不等于病区、护理单元或地点；服务方向、接诊形式、换房间都不产生新单元。

**日期规则**

- 业务有效期只存日期，不含时分秒；起止都含当日，结束为空表示长期有效。
- “10-31 止”表示 10-31 当天仍有效，下一版本从 11-01 起。
- 同一对象的版本期间不重叠。修订在生效日 D 生效时，旧版结束日 = D 前一日，新版开始日 = D。
- 允许设未来生效日（计划生效）。
- 审计时间（谁在何时提交、确认）用不带时区的时间戳（timestamp without time zone），与业务日期分开；一律是医院所在地的本地时间，不做时区转换。
- 注意：这与 CONTEXT.md 中“只填日期视为当日零点、结束时刻本身有效”的约定不同，是有意的偏离；日后与旧资产对接时需做映射。

## 3. 数据模型

```
主体 ──(运营等关系，带期间)── 院区
部门 ─────────┐
院区 ─────────┼── 服务单元（部门 × 院区 × 运营主体 × 期间）
运营主体 ─────┘
```

**物理表（首版；部门深化、外部代码、组织变更后的完整表清单见 `docs/database/README.md`）**

| 表 | 作用 |
| --- | --- |
| institution / institution\_version | 主体：身份表（id、code）与版本表 |
| campus / campus\_version | 院区：身份表与版本表 |
| operator\_relation | 主体—院区关系：每行自带期间，端点不可改，调整 = 关闭旧行 + 新建行 |
| department / department\_version | 部门：身份表与属性版本表（D1 起，迁移 0006；首版曾是无版本的引用表）；隶属、关系、分类、别名、外部代码见第 13 节 |
| service\_unit / service\_unit\_version | 服务单元：身份表与版本表 |
| service\_unit\_lineage | 拆分/合并的前身与后继：前身 id、后继 id、类型、变更申请、生效日 |
| change\_request | 变更申请：一张申请可含多项变更，存前后内容、状态、提交人/确认人及时间、可选变更说明 |
| option\_item、approval\_rule（配置） | 选项（节点角色、单元类型等）；谁能确认哪类变更、是否允许自确认 |

版本表统一带：id、version\_no、valid\_from、valid\_to、change\_id、recorded\_at、recorded\_by。

**字段（草案，必填项以字段矩阵为准，首版只对名称等核心项必填；带 \* 为建议必填）**

| 对象 | 字段 |
| --- | --- |
| 主体 | 名称\*、主体性质\*、统一社会信用代码、医疗机构登记代码、执业许可证号、许可证有效期起止 |
| 院区 | 代码\*（身份）、名称\*、节点角色\*、地址、行政区划代码、电话、实际启用日期、运营状态\*（筹建/试运行/运行/停用） |
| 运营关系 | 主体\*、院区\*、关系类型\*（运营/登记/管理/收费）、是否主要运营方\*、期间\* |
| 部门 | 代码\*（身份）；属性与组织生命周期（筹备 / 正式履职 / 暂停履职 / 撤销 / 被替代）在版本里，见第 13 节 |
| 服务单元 | 代码\*（身份）、名称\*、所属部门\*、院区\*、运营主体\*、单元类型\*、电话、范围说明、期间\*、状态\*（在用/暂停/已退出） |

单元类型沿用现有码值 OPD/IPD/ED/EXAM/LAB/PHARMACY/OR/OTHER，中文名称按统一语言；“医技单元”的编码映射需在后续获授权的分类设计中明确，不新增码值、不重释既有码值。负责人字段不设。

**约束**

- code 全局唯一，含已退出对象，永不复用。
- 同一对象的版本期间不重叠（由 PostgreSQL 的 daterange 排他约束在数据库层保证）。
- 运营关系：同一院区在重叠期间最多一个主要运营方；只有“运营”类型可为主要运营方；端点不可改。**同一主体与同一院区，同一时期只能有一条关系（不论类型）**；要换类型 = 关闭旧关系（最后有效日 D-1）+ 自 D 新建。（2026-10-19 Peter 决定，迁移 0013）
- 服务单元每个版本：所属部门在用；院区非停用；运营主体与该院区存在覆盖整个单元期间的“运营”关系。
- 业务表无物理删除。

## 4. 变更与审批

- 状态：草稿 → 已提交 → 已确认（生效）/ 已退回。
- 一张申请可含多项变更，整体成立或整体不成立：拆分、合并、“新建部门 + 新建服务单元”都用这种方式。
- 提交和确认是两次独立动作，各自记录人和时间。系统不提供“创建即生效”的捷径，导入也不例外：初始导入作为一张批量申请，确认一次。
- 允许同一人提交并确认，由配置开关控制（默认开）；开关关闭后须由不同人确认。一人时也必须走完确认这一步。
- 确认页展示前后差异；确认时重新校验，校验不通过不能确认；退回必须写原因。
- 变更说明为可选的一段文本，无附件、无校验。
- 确认规则按对象类型 × 动作配置，改规则不改代码。
- 所有写入只经变更申请，不提供绕过入口。

## 5. 动作与校验

| 对象 | 动作 | 要点 |
| --- | --- | --- |
| 主体 | 新建、修订 | 主体不设有效/暂停/终止业务状态；终止关系通过关闭运营关系表达 |
| 院区 | 新建、修订资料、变更运营状态 | 状态：筹建 → 试运行 → 运行 → 停用；代码永久，停用后不复用 |
| 运营关系 | 建立、关闭 | 调整期间或是否主要方 = 关闭旧行 + 新建；校验主要运营方互斥 |
| 部门 | 新建、修订、变更组织生命周期、分类、隶属、组织变更等 | 见第 13 节与 `docs/部门组织变更-评估与分期.md`；首版的“改名、停用 / 恢复”只保留读取 |
| 服务单元 | 新建 | 通过上述版本约束校验 |
| 服务单元 | 修订 | 名称、电话、范围说明；身份不变 |
| 服务单元 | 重新绑定 | 换院区或运营主体；显式动作，新版本 |
| 服务单元 | 更换所属部门 | 显式动作，新版本；旧日期回溯仍显示当时的部门 |
| 服务单元 | 暂停/恢复 | 新版本改状态 |
| 服务单元 | 永久退出 | 终态，不可恢复，代码不释放 |
| 服务单元 | 拆分 | 旧单元退出，新建 ≥2 个后继（新身份、新代码），写演变关系；一张申请整体成立 |
| 服务单元 | 合并 | ≥2 个旧单元退出，新建 1 个后继，写演变关系；一张申请整体成立 |

拆分/合并不自动迁移任何下游引用；MVP 内也尚无这些引用。

**阻止规则**：关闭运营关系或停用院区时，若仍有在用单元依赖它，确认被阻止并列出受影响单元，须先对这些单元重新绑定或退出。

## 6. 查询与读取

- 列表页顶部“查看日期”，默认今天，显示该日有效的版本；每个对象可看版本时间线。
- “某院区有哪些部门”不单独存：该日在该院区有效的服务单元，按所属部门去重。
- 部门名称按查看日期取当时的版本（D1 起）。
- 最小只读输出：按日期导出 CSV 和简单只读接口，供其他系统取用（第三步）。
- **组织总览**（剧本 21，“组织与关系”第一项，`/organization-overview`）：只读，不新增写入，不改表结构。
  - 服务布局桑基图只计服务单元，带宽 = 单元数，反映服务配置分布，不代表床位、人力或诊疗量。两种视角：**按分类**（一级部门的部门管理主分类 → 一级部门 → 二级部门 … → 服务单元）、**按院区**（院区 → 单元所属部门，只两列）。单元挂在它自己所属的部门上，不上卷：二级部门的单元连到二级部门。
  - 多列只在树形结构上用：每个部门只有一个上级、每个一级部门只有一个主分类，路径不会拼出不存在的组合；院区视角若再加一列，会让不同院区的单元在部门节点处混在一起，所以只两列。
  - 部门 × 院区矩阵：格子是部门本身（不含下级）在该院区的单元数与类型；空格写“—”，只表示**未登记**，不表示院方确认不设（系统里没有“确认不设”的数据）。
  - 默认只计当天在用的单元；“含计划中”“含暂停”由人打开。概况（正式履职部门、在用 / 暂停 / 计划单元、跨院区部门、没有在运营单元的部门）只随查看日期变化，不受图内筛选影响。
  - 编码治理图：来源系统 → 字典 → 解释状态（指向部门 / 指向服务单元 / 部门与单元都有 / 对象未建模 / 待裁决），按源记录去重计数，分母是已登记到台账的源记录。
  - 查看日期、视图与筛选写在地址栏，复制链接可恢复同一视角。汇报模式与图片导出放第二步。

## 7. 验收剧本

每条都要由非开发人员独立走完，提交与确认分别留痕。

1. 登记高新院区（筹建），绑定运营主体，变更运营状态。
2. 为心内科在高新院区设立门诊、住院两个服务单元（同部门同院区多单元）。
3. 单元更名；再把一个单元从本部重新绑定到高新，身份不变。
4. 单元暂停再恢复；永久退出后试图复用其代码被拒。
5. 查指定日期哪些单元在运营、归哪个主体。
6. 把一个服务单元拆成两个。
7. 把两个服务单元合并成一个。
8. 把一个院区的单元改挂到新建部门下，再按旧日期回溯，看到的仍是改挂前的部门。

部门深化新增（2026-10-15，见第 13 节）：

9. 新设一个筹备中的部门，计划次年 1 月 1 日正式履职：之前不计入部门数，之后计入。
10. 部门更名：按旧日期查询显示旧名称；曾用名、别名都可检索。
11. 调整部门主分类：旧赋值保留在历史中；同一时点只有一个主类。
12. 部门在新院区开展服务（新建或重新绑定服务单元）：部门 ID、管理编码不变。
13. 调整行政隶属：同一视图同一时点一个上级，试图成环被拒；一级 / 二级部门随之变化；专业管理关系不受影响。
14. 行政隶属调整后，外部身份映射（HIS、病案等）原样不变。
15. 一份 HIS 字典混装不同对象：代表全院部门的代码映射到部门，“本部心血管门诊 / 住院”映射到各自的服务单元；同一代码同一时点不能同时映射部门与单元；按部门汇总经服务单元的所属部门得出；只登记未解释的记录为待裁决，不进入导出；护理单元、病区等代码标“对象未建模”。
16. 同一个病案科室分类代码分别赋给一个部门和一个服务单元：按旧日期回溯看到当时的分类；共同类别不使两者成为同一对象；部门分类不自动下发给其服务单元。
17. 历史代码复用：同一外部代码在不同期间指向不同对象，按日期还原当时指向谁；同一代码在不同院区按条件指向不同对象。
18. （人员域之后）负责人更换，部门身份不变；岗位空缺不影响部门存在。

组织总览新增（2026-10-21，只读）：

21. 领导查看某日全院服务布局，点选一个部门，核对它在各院区的单元，并跳转到某个单元的详情。

剧本走不通时用三分法定位：事实有分歧，找责任人定；事实一致但系统表达不了，改模型；系统能表达但操作不顺，改页面。新增对象或表的唯一理由，是某条剧本因它而失败。

- 服务单元类型不允许修订；职责变化走拆分或新建。
- 关闭运营关系或停用院区时，若仍有在用单元依赖它，阻止确认并列出受影响单元，须先对这些单元重新绑定或退出。

- 组件底层采用 Base UI（shadcn 风格 base-mira，图标 hugeicons），全项目统一；ReUI 组件同样选 Base UI 版本。（2026-10-13 由 Radix 改为 Base UI）
- 单元类型中文名：沿用旧仓库院内建议码表，按统一语言把“业务单元”改称“单元”——门诊单元、住院单元、急诊单元、检查执行单元、检验执行单元、药房、手术服务单元、其他；码值不变，名称在 option\_item 中可调。（2026-10-14）
- “某日在运营的单元”= 当天有有效版本的单元，含暂停（以状态标出）；尚未生效的计划单元、已退出的单元不算。（2026-10-14）

**时间与时区**：本应用只在一个小地域使用，所有日期和时间都按本地时间处理，不引入时区。日期用 date，时间戳用 timestamp without time zone，不使用 timestamptz，前后端统一。写入时间由数据库取本地当前时间（LOCALTIMESTAMP）；为避免数据库主机系统时区设成 UTC 而写错，应用连接数据库时固定使用本地时区（配置项 HDIP\_TIMEZONE，默认 Asia/Shanghai），这只决定“现在是几点”，存进去的值仍不带时区。

## 11. 技术栈与实现约定

后端用 Python（FastAPI），数据库用 PostgreSQL，前端按你的选择；两端之间用 OpenAPI 生成的类型和 TanStack Query hooks 连接。

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite（单页应用，无 SSR） | 内网管理端，不需要服务端渲染 |
| UI | shadcn/ui（Base UI 版本，base-mira 风格）+ ReUI + Tailwind CSS | 组件按需复制进项目，无运行时依赖；需要时可用 ReUI 的 Data Grid、Filters、Date Selector（Base UI 版本） |
| 数据请求 | TanStack Query | 查看日期作为查询键的一部分；确认后使相关查询失效重取 |
| 后端 | Python + FastAPI + Pydantic v2 | 沿用已有的 FastAPI 经验 |
| 数据访问 | SQLAlchemy 2.0 + Alembic | 原生支持日期范围类型与排他约束；约束和索引在迁移里手写 SQL |
| 数据库 | PostgreSQL 18 | 排他约束、部分唯一索引、事务 |
| 接口契约 | FastAPI 自动生成 OpenAPI，再用 orval 生成 TypeScript 类型与 TanStack Query hooks | 前后端语言不同，靠契约生成保持一致 |

**为什么后端选 Python 而不是 Node**

1. 需求的核心在数据库层：版本期间不重叠、主要运营方互斥、多项变更整体成立。SQLAlchemy 与 Alembic 原生支持范围类型和排他约束；Node 一侧常见的 ORM（如 Prisma）对这两样支持有限，最终也要绕开 ORM 手写 SQL。
2. 已有 FastAPI 的使用和运维经验，少引入一项新技术。
3. OpenAPI 加 orval 能补上前后端语言不同的短板，前端拿到的是生成的类型和请求 hooks。
4. 之后导入 HIS 部门字典、做数据质量校验（研究报告推荐的 GX Core 是 Python 工具）可以用同一种语言。

代价：校验规则前后端各有一份，前端只做即时提示，以数据库和后端为准。Node 方案的优势是前后端共享校验与类型，用 Kysely 加手写 SQL 也能实现同样的数据库约束，所以两者都可行，选 Python 主要因为上面第 1、2 点。

**实现约定**

- 一个 API 服务加一个 PostgreSQL；MVP 不引入 Redis、Kafka 或消息队列。
- 规则放在数据库层强制：code 唯一、期间排他、外键、检查约束；应用层校验只负责给出可读的错误信息，两者不一致以数据库为准。
- 业务表不开放直接增改接口：API 只有“创建、提交、确认、退回申请”和只读查询；确认在一个事务里应用全部变更项，失败整体回滚。
- 日期：数据库用 date 和 daterange（含两端），接口用 YYYY-MM-DD 字符串，审计时间戳用不带时区的 timestamp，接口用不带时区的 ISO 日期时间字符串（如 2026-10-13T09:30:00），前后端都不做时区转换，按原样显示，不使用 timestamptz。
- 变更申请的前后内容存 JSONB。
- 应用账号不授予 DELETE 权限，保证无物理删除。
- 单仓库两个包（web、api）加一个迁移目录。
