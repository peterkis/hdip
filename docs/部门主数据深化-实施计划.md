2026-10-15 · 状态：**定稿**（Q1–Q7 已定，见第 9 节）· **D1 已完成**（迁移 0006，剧本 9–12）· **D2 已完成**（迁移 0007，剧本 13）· **D3 已定稿**（第 10 节）· 原型：https://claude.ai/artifact/PuuVApSrT9EG1cgm1yW3kS · 数据库设计：[docs/database/README.md](database/README.md) 第 6 节

## 1. 需求要点

部门回答“谁在医院组织体系内承担这组职责”。它的身份不因服务院区、办公地点、负责人、具体人员、服务形态或核算口径的变化而自动改变。

| 对象 | 回答什么 | 不应被什么替代 |
| --- | --- | --- |
| 主体 | 谁设立、授权、运营或承担责任 | 院区名称 |
| 部门 | 谁在组织体系内承担这组职责 | 专业分类、HIS 科室代码 |
| 院区 | 在哪个院区范围开展活动 | 一个必然存在的行政父部门 |
| 服务单元 | 哪个运营单元承接具体服务流程 | 部门本身、一条医疗服务项目 |
| 地点 | 业务实际发生在哪个空间 | 部门、护理团队 |
| 核算单元 | 按什么范围归集、分配和分析经济事项 | 部门的另一个名称 |

## 3. 逻辑数据集与物理结构

沿用现有做法：身份表、版本表、带期间的关系表、只经变更申请写入，`daterange` 加排他约束，触发器保护历史。

| 逻辑数据集 | 物理表 | 粒度 | 主要内容 |
| --- | --- | --- | --- |
| 部门身份 | `department`（已有） | 一个真实部门 | 稳定 ID（不含院区、类别、上级含义）、院内管理编码 `code`、身份来源 |
| 部门属性版本 | `department_version`（新增） | 一个部门的一个有效版本 | 正式名称、简称、职责说明、设立形式（常设 / 经批准的临时部门 + 期限）、组织生命周期、行政级别（选填）、承担职责（自由标签）、依据文本（选填） |
| 别名 | `department_alias`（新增） | 一条别名 | 类别（别名 / 检索码）、值、期间。曾用名由版本推出，不另存 |
| 分类方案 | `classification_scheme`、`classification_code`（新增，配置） | 一个方案的一个版本、一个代码 | 方案名、版本、用途、是否单选（主分类单选，承担职责多选）、代码与中文名 |
| 部门分类赋值 | `department_classification`（新增） | 一次赋值 | 部门、方案、代码、生效期间（默认当天）。单选方案在同一时点只能有一个赋值（部分排他约束）；经变更申请（Q2） |
| 部门主体归属 | `department_institution`（新增） | 一条归属关系 | 部门、主体、是否主归属、期间。同一时点只有一个主归属 |
| 组织视图 | `org_view`（新增，配置） | 一个视图 | 视图代码、名称、用途、单一上级约束。首期只有“行政视图” |
| 组织视图 | 见上行 | — | 首期启用“行政视图”；运营、病案视图先占位（Q6） |
| 行政隶属 | `department_hierarchy`（新增） | 视图内一条上下级边 | 视图、上级部门、下级部门、期间。同一视图、同一时点一个直接上级，禁止成环。一级 / 二级部门由此计算 |
| 部门管理关系 | `department_relation`（新增） | 一条关系 | 类型（专业管理 / 协作 / 院区管理）、双方、管理事项或协作范围、期间 |
| 部门—服务单元责任关系 | 现有 `service_unit_version.department_id` = 所属部门 | — | 只保留所属部门，不加其他关系（Q7） |
| 外部身份映射 | `external_code` + `external_code_assignment`（新增，D3 定稿见第 10 节） | 一条源记录；源记录在某段期间的解释 | 来源系统实例、字典、外部代码；解释指向部门 / 服务单元 / 对象未建模，可带院区条件，带期间。“待裁决”= 有源记录但该日没有解释 |
| 分类关联 | `department_classification`、`service_unit_classification` | 一次赋值 | 外部分类方案（病案科室分类、业务科室分类等）作为分类方案登记；部门与单元的关联含义分开 |
| 负责人 | 不建表 | — | 详情页显示“当前负责人”，来自将来“岗位与任职”的有效任职关系 |

码值沿用旧仓库院内建议码表：映射性质 `EXACT/BROADER/NARROWER/RELATED/UNRESOLVED`，标识类别 `ALIAS/SEARCH_CODE`。旧 `org_type` 混合了多个维度（临床、护理、后勤……），由本次的“部门管理主分类”取代，不再沿用。

## 4. 业务规则与约束

1. **身份**：部门 ID、管理编码永久不变、不复用。更名、调整分类、调整隶属、搬院区都沿用原身份。
2. **版本**：属性修订遵循现有规则：只作用于最新版本，生效日 D，旧版止于 D-1，内容无变化则拒绝。
3. **生命周期**：
   - 只能沿 筹备 → 正式履职 ⇄ 暂停履职 → 撤销 变化。
   - 撤销是终态，不能恢复；以后重设需新建身份。
   - 临时部门必须填期限；期满后由一张申请撤销或转为常设，不自动执行。
4. **统计口径**：部门数只计查看日期当天“正式履职”的部门。筹备、暂停、撤销分别列出，不计入。按主分类计数时，每个部门只计一次。
5. **主分类**：同一方案、同一版本、同一时点只有一个赋值（数据库部分排他约束）。调整 = 结束旧赋值 + 新建赋值，历史保留。
6. **行政隶属**：
   - 同一视图、同一时点只有一个直接上级（排他约束）。
   - 禁止成环：在一张申请全部应用后统一检查，与现有 `_check_units` 同一位置。
   - 树深度不保存，查询时计算。
   - **一级 / 二级部门**指行政视图中的组织层级（不是专业分类层级，也不是 HIS 菜单分组）：没有上级的是一级部门，上级是一级部门的是二级部门，例如信息中心之下的图书室、计算机中心。层级由关系计算，不保存。子部门本身也是部门。
7. **专业管理、协作**：多对多，按事项或范围各自记录，不改变行政隶属；软件不从名称推断。
8. **外部映射**：
   - 行政隶属、主分类调整都不改动映射。
   - 映射性质为“待裁决”的条目不能用于导出口径。
   - 同一外部代码同一时点可以映射到多个部门，但必须标明性质。
9. **服务单元**：单元每个版本要求所属部门在单元期间内为“正式履职”，类比院区（Q1 已定）。部门暂停或撤销时，若仍有依赖它的单元，按现有阻止规则列出受影响单元。
10. **写入**：业务数据（含部门的主分类赋值）全部经变更申请。分类字典是配置，维护人可直接维护、不需确认（Q2）。

## 9. 决定

### 2026-10-15 第一轮

- **Q1 生命周期**：五态。
  - `PREPARING` 筹备 → `ACTIVE` 正式履职 ⇄ `SUSPENDED` 暂停履职 → `REVOKED` 撤销（终态）。
  - `SUPERSEDED` 被替代：终态，拆并预留。
  - 服务单元期间内部门须为正式履职；部门暂停或撤销时，若仍有单元依赖，阻止确认并列出受影响单元。

### 2026-10-15 第二轮（Peter）

- **Q2 主分类**：
  - **分类字典**（方案与代码）是配置：不记启用日，不设确认方；有维护人角色即可直接维护，不需确认，记录维护人与时间；代码不删除，只停用。
  - **部门上的主分类赋值**是业务变更：照常经变更申请，按确认规则提交、确认；赋值带生效日，默认当天，可改。
  - 权限：本期沿用三角色（只读用户只能看）；代码里以“权限键”判断，便于以后细化权限。
- **Q3 承担职责**：本阶段用**自由标签**起步（改变第一轮的“固定选项”）。
- **Q4 依据**：**维持设计文档决策 3**，不使用批文、引文、依据机制。只在部门属性版本上可选填一段依据文本（文号或说明），不做依据对象，不校验。
- **Q5 行政级别**：首期要，选填。
- **Q6 视图**：首期做行政视图；运营、病案视图设计好并占位。
- **Q7**：只保留现有的“所属部门”，不加其他部门—服务单元关系。
- **一级 / 二级部门**：指行政视图中的组织层级，即子部门；例如信息中心之下的图书室、计算机中心。
- **主分类示例**：

  | 部门 | 主分类 |
  | --- | --- |
  | 心血管内科 | 临床诊疗类 |
  | 医务部 | 行政与业务管理类 |
  | 检验科 | 医疗技术类 |
